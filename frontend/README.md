# Travel CRM: фронтенд

Веб-интерфейс сотрудников: менеджера, руководителя и бухгалтера. Vue 3, TypeScript, Vite, Pinia, Vue Router, библиотека компонентов Naive UI. Состав функций описан в [ТЗ](../docs/technical-specification.md), решения по стеку и запуску — в [архитектуре](../docs/architecture.md).

## Требования

- Node.js 22.13 или новее (рекомендуется актуальная LTS-версия 22);
- npm.

## Установка и запуск

```bash
cd frontend
npm ci
cp .env.example .env.local
npm run dev
```

Приложение откроется на `http://localhost:5173`. Запросы `/api` dev-сервер проксирует на бэкенд; адрес задаётся переменной `VITE_API_TARGET` в `.env.local` (по умолчанию `http://localhost:8000`). Сам браузер всегда обращается к `/api` своего адреса: в Docker такой же адрес обслуживает nginx.

### Работа без бэкенда

Пока сервера авторизации нет, в режиме разработки (`npm run dev`) страница входа предлагает выбрать роль без пароля. Это временный демонстрационный вход, он заменяется настоящей формой в задаче «Вход, выход и доступ по ролям». В собранной версии демонстрационного входа нет.

Сессия хранится только в памяти страницы: после перезагрузки приложение пробует восстановить её через refresh-cookie, а без сервера возвращает на страницу входа. В консоли браузера при этом виден ожидаемый ответ 502 на `/api/auth/refresh`.

## Команды

| Команда | Назначение |
|---|---|
| `npm run dev` | Dev-сервер с горячей перезагрузкой |
| `npm run build` | Проверка типов и production-сборка в `dist/` |
| `npm run type-check` | Проверка типов (`vue-tsc`) |
| `npm run lint` | Линтеры `oxlint` и `eslint` (с автоисправлением) |
| `npm run format` | Форматирование `prettier` |
| `npm run test:unit` | Тесты `vitest` в режиме наблюдения; `npx vitest run` — один прогон |

Если `npm install` на npm 10.9 падает с ошибкой `Cannot read properties of null (reading 'edgesOut')`, это известный баг npm при разборе зависимостей. Для установки по lock-файлу используйте `npm ci`; при изменении зависимостей запускайте `npx npm@11 install`.

## Структура

```
src/
├─ api/          HTTP-клиент, обработка ошибок, обновление токена
├─ auth/         роли и список разделов (меню и права строятся из него)
├─ components/   общие компоненты
├─ layouts/      общий макет: меню, шапка
├─ router/       маршруты и защита по ролям
├─ stores/       состояние (Pinia): сессия
└─ views/        страницы разделов
```

### Как устроены запросы

Модули API (`src/api/*`) получают клиент через `useHttp()`. Клиент добавляет access-токен, при ответе 401 один раз обновляет его через `POST /api/auth/refresh` и повторяет запрос; параллельные запросы ждут один общий refresh. Если сессию восстановить нельзя, она очищается и открывается страница входа. Все ошибки приводятся к `ApiError` с полями `code`, `message`, `fields[]`, а сообщения для недоступного сервера, 401, 403 и 5xx написаны по-русски.

### Как добавить раздел

1. Добавьте запись в `NAVIGATION` (`src/auth/navigation.ts`) с названием, адресом и ролями.
2. Создайте страницу в `src/views/` и подключите её в `sectionViews` (`src/router/index.ts`).

Меню и защита маршрутов используют один и тот же список, поэтому права в них не расходятся. Окончательную проверку прав всегда выполняет сервер.

## Допущения до согласования контракта API

Имена полей ответа входа и обновления токена (`access_token`, `user.full_name`, `user.role`) и значения ролей (`manager`, `head`, `accountant`) приняты по [проекту архитектуры](../docs/architecture.md). Они уточняются в задаче «Согласовать контракт API»; при расхождении правятся `src/api/auth.ts` и `src/auth/roles.ts`.
