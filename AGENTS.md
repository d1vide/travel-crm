# Работа с TravelCRM

## Источники решений

Перед изменениями прочитать `docs/technical-specification.md` и `docs/architecture.md`. Учебные материалы `docs/product/` описывают более широкий продукт: Telegram, договоры и реальные интеграции не входят в текущую реализацию.

Проект модели данных по #6 находится в `docs/data-model.md`, переходы статусов — в `docs/state-transitions.md`. Точные имена предлагаемых DTO, enum и примеры находятся в `docs/api/README.md`, `docs/api/domain.schema.json`, `docs/api/domain.examples.json`. Пока это проект для согласования с фронтендом; спорные решения перечислены явно. Не считать существующим API то, что описано только схемой DTO. HTTP-контракт согласуется в #7, генерация клиента — в #26.

## Изменения

- Сохранять имена ролей и полей существующей авторизации. Деньги передавать десятичными строками; сервер отвечает за суммы, права и переходы статусов.
- Не смешивать статусы заявки, брони, платежа и возврата. Не заменять снимок тура изменяемой записью каталога.
- При изменении модели обновлять документацию, схему и примеры вместе. При появлении Pydantic/OpenAPI сверить их с проектом модели и назначить единый источник HTTP-контракта.
- Не раскрывать публичным страницам и бухгалтеру полные персональные карточки. Использовать только вымышленные тестовые данные.
- Работать в ветке задачи, описывать результат и проверку в PR. Не закрывать #6 без подтверждения совместимости с фронтендом.

## Проверки

Фронтенд: из `frontend/` выполнить `npm ci`, `npm run type-check`, `npm run test:unit -- --run`, `npm run build`. `npm run lint` исправляет файлы, поэтому проверять его diff. Правки только документации не требуют повторной сборки приложения, если модели исполняемого кода не менялись; JSON Schema и примеры нужно валидировать. Команды бэкенда появятся с его каркасом в #9.
