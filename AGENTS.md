# Работа с TravelCRM

## Источники решений

Перед изменениями прочитать `docs/technical-specification.md` и `docs/architecture.md`. Учебные материалы `docs/product/` описывают более широкий продукт: Telegram, договоры и реальные интеграции не входят в текущую реализацию.

Зафиксированная модель данных по #6 находится в `docs/data-model.md`, переходы статусов — в `docs/state-transitions.md`. Контракт 0.2 находится в `docs/api/openapi.json`; обзор и правила интеграции — в `docs/api/README.md`, результат проверки текущего фронтенда — в `docs/api/frontend-review.md`. JSON Schema и примеры DTO/команд — в `docs/api/domain.schema.json` и `domain.examples.json`. Контракт зафиксирован после проверки по поручению владельца, но серверные эндпоинты ещё реализуются. Генерация клиента — #26.

## Изменения

- Сохранять имена ролей и полей существующей авторизации. Деньги передавать десятичными строками; сервер отвечает за суммы, права и переходы статусов.
- Не смешивать статусы заявки, брони, платежа и возврата. Не заменять снимок тура изменяемой записью каталога.
- При изменении модели обновлять документацию, схему и примеры вместе. До бэкенда OpenAPI собирается `docs/api/build_openapi.py`; не редактировать его вручную. При появлении Pydantic сверить экспорт с зафиксированным контрактом; затем заменить временный генератор экспортом из кода, сохранив один источник HTTP-контракта.
- Не раскрывать публичным страницам и бухгалтеру полные персональные карточки. Использовать только вымышленные тестовые данные.
- Работать в ветке задачи, описывать результат и проверку в PR. Совместимость модели с текущим каркасом и сценариями проверена в `docs/api/frontend-review.md` по поручению владельца; отдельное согласование коллегой не заявлять. Закрытие задачи требует попадания результата в main.

## Проверки

Фронтенд: из `frontend/` выполнить `npm ci`, `npm run type-check`, `npm run test:unit -- --run`, `npm run build`. `npm run lint` исправляет файлы, поэтому проверять его diff. Правки только документации не требуют повторной сборки приложения, если модели исполняемого кода не менялись. Контракт: `uv run docs/api/validate_contract.py`; после правок реестра/схем сначала `uv run docs/api/build_openapi.py`.

Бэкенд: `uv sync --directory backend --frozen`, `uv run --directory backend ruff check .`, `uv run --directory backend ruff format --check .`, `uv run --directory backend pytest -q`. Для pytest требуется TEST_DATABASE_URL PostgreSQL 16 с именем БД на _test: тесты создают и удаляют только свои случайные схемы. Не подменять PostgreSQL на SQLite и не пропускать интеграционные тесты из-за отсутствующей БД. Схема приложения изменяется только Alembic. Локальный .env создаётся `python scripts/init_env.py` и не попадает в Git; seed не перезаписывает существующие учётные записи. Правила запуска — в `backend/README.md`.

Реализованы auth/health, clients, десять операций requests/users/history по #13, чтение каталога tours по #30 и три операции communications по #16. Правила подключения — в docs/api/*-integration.md. Подборки и публичные ссылки реализованы в #31 (миграция 0006); туристы и их публичная форма реализованы в #32 (миграция 0007); пять операций бронирований реализованы в #14 (миграция 0008), включая ограничения действующей брони в заявках/подборках/туристах; пять операций оплаты и HTTP-заглушка реализованы в #15 (миграция 0009). Уведомления, финансовые брони, complete и независимая доставка результатов реализованы в #33 (миграция 0010); правила — docs/api/payment-notifications-integration.md. Три команды отмены брони реализованы в #34 без изменения схемы; контракт — docs/api/booking-cancellation-integration.md. Пять операций возврата реализованы в #35 (миграция 0011); контракт — docs/api/refunds-integration.md. При изменении возвратов сохранять проверки completion/resume и проекции финансовых сумм; проекции и allowed_actions добавлять вместе с проверками дочерних данных. При изменении заявки или создании общения сначала блокировать Client, затем Request, чтобы доступ сериализовался с переназначением. Runtime /openapi.json — поднабор, полная согласованная спецификация находится в docs/api/openapi.json; не заменять её неполным экспортом при подключении фронтенда.

Сводный отчёт #36 реализован без миграции; контракт — docs/api/reports-integration.md. Границы периода вычисляет PostgreSQL в Europe/Moscow; четыре агрегата используют один снимок, суммы оплат и возвратов отдельные.

Общий обработчик ошибок #18 сохраняет Error, русские field messages, WWW-Authenticate/Allow и no-store; правила — docs/api/errors-integration.md. Не отражать input/ctx/detail исключений или внутренние заголовки в ответ.
