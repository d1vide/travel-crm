# Travel CRM


Курсовой проект по дисциплине ПКИС, группа ЭФМО-01-25.


**Тема:** «Создание программного решения для автоматизации процесса управления клиентскими отношениями в туристической компании».


## Назначение


Веб-сервис для работы туристической компании с клиентами: ведение заявок, подбор туров по предпочтениям, управление бронированиями, учёт платежей, история общения и базовая отчётность.


В учебной версии используется тестовый каталог и заглушка платёжного сервиса. Бронирование у поставщика менеджер выполняет вне CRM и вносит его ответ в систему.


## Текущий статус


В карточке заявки менеджер собирает подборку, выдаёт публичные ссылки, проверяет данные туристов, фиксирует ответ поставщика и создаёт платёж. Публичная страница подборки и форма туристов доступны по ссылкам без входа. В разделе оплат есть финансовая сводка, а менеджер и руководитель получают уведомления о зачислении. Историю общения можно вести в карточках клиента и заявки. При отмене брони в карточке фиксируются причина и ответ поставщика. Возврат оформляется отдельно. [Обзор API](docs/api/README.md)

Сервер возвратов #35 реализован: [подключение](docs/api/refunds-integration.md). Интерфейс возвратов подключается отдельно. Серверные критерии рабочего места руководителя #17 покрыты существующими API; Сводный отчёт #36 реализован на сервере: [подключение](docs/api/reports-integration.md).

Для уже существующего `.env` перед запуском оплаты выполнить `python scripts/init_env.py --add-payment-settings`: добавятся только недостающие настройки интеграции.

Показ назначен на 04.12.2026. Порядок реализации — в [плане #46](https://github.com/d1vide/travel-crm/issues/46) и [roadmap](docs/roadmap.md): сначала заявки #13 и каталог #30, затем подбор и бронь, затем оплата.

## Совместная работа


Задачи ведутся в [Issues](https://github.com/d1vide/travel-crm/issues). Обычные изменения выполняются в отдельных ветках, сохраняются коммитами и объединяются в main через Pull Request после проверки. Владелец и соавтор с правом записи также могут делать прямые коммиты в main. Одобрение второго участника доступно, но не обязательно. Подробности — в [правилах команды](docs/team.md).


Модель данных, переходы статусов и контракт API 0.2 зафиксированы. Типы фронтенда уже генерируются командой `npm run gen:api`. Экспорт полной спецификации из кода и оставшиеся части #26, как и CI #25, перенесены после показа. Текущие проверки выполняются локально; бизнес-права и проверки дополняются с каждым модулем.


## Запуск


На новом окружении выполните `python scripts/init_env.py`. Если локальный `.env` создан до появления оплаты, выполните `python scripts/init_env.py --add-payment-settings`. Затем запустите `docker compose up -d --build --wait`. Compose запускает PostgreSQL, FastAPI, платёжную заглушку и nginx с интерфейсом на http://localhost:8080. [Подробности запуска](backend/README.md)

Фронтенд запускается отдельно по [frontend/README.md](frontend/README.md) на localhost:5173 и проксирует /api на бэкенд. Для нативной разработки после подготовки PostgreSQL: `uv sync --directory backend --frozen`, затем `uv run --directory backend python -m app.bootstrap`.

Перед показом выполните `docker compose exec backend .venv/bin/python -m app.preflight --web-url http://web:8080`. Команда проверяет готовность демо-окружения без изменения данных. [Подготовка стенда, демо-сотрудники и сценарий](docs/demo-preparation.md); [результаты и ограничения приёмки](docs/test-report.md). Проверка чистого контейнерного запуска остаётся в #24.
