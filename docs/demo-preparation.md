# Подготовка демонстрационного стенда

Серверная часть подготовки #20. Дата проверки: 26.11.2026. Полная приёмка пока частичная: [отчёт](test-report.md). Проверка не подтверждает готовность незавершённых экранов и не заменяет запуск Compose на чистой машине (#24).

## Первый запуск

Из корня проекта, при установленных Python и Docker Engine с Compose:

```sh
python scripts/init_env.py
docker compose config --quiet
docker compose up -d --build --wait
docker compose exec backend .venv/bin/python -m app.preflight --web-url http://web:8080
```

Первый скрипт создаёт локальный `.env` со случайными секретами, `SEED_DEMO=true` и паролем демонстрационных сотрудников. Старый `.env` сохраняется. Для окружения, созданного до оплаты: `python scripts/init_env.py --add-payment-settings`. Пароль берётся из локального `DEMO_PASSWORD`; `.env` не передаётся вместе с проектом и не включается в журнал проверки.

Приложение открывается на `http://localhost:8080` (если WEB_PORT изменён — на выбранном порту). Внутри контейнера web доступен как `http://web:8080`: флаг `--web-url` меняет только адрес диагностических GET-запросов. Рабочий PUBLIC_APP_URL должен оставаться адресом браузера, одинаковым у backend и stubs.

Backend при старте применяет Alembic до head и запускает seed при SEED_DEMO=true. Seed создаёт трёх вымышленных сотрудников и тестовый каталог. Существующие учётные записи, их пароли, рабочие профили и изменённые предложения каталога он не перезаписывает.

| Вход | Роль |
|---|---|
| manager@example.com | Менеджер |
| head@example.com | Руководитель |
| accountant@example.com | Бухгалтер |

Если пароль в `.env` менялся после первого seed, старые учётные записи сохраняют прежний пароль. Команда проверки обнаружит несовпадение; повторный seed его не исправляет. Для показа используйте известные учётные записи или отдельное новое демонстрационное окружение.

## Проверка перед показом

`app.preflight` возвращает код 0, только если все семь проверок прошли; при проблеме — код 1 и короткую подсказку. Исключения, адреса БД, пароли, ключи, токены и ответы провайдера не печатаются.

1. Схема БД соответствует актуальной head-миграции.
2. Три демо-сотрудника активны, имеют ожидаемые роли и пароль из текущих настроек.
3. В каталоге есть активное предложение.
4. Web возвращает HTML приложения.
5. `/api/health/ready` доступен через web/nginx.
6. `/healthz` платёжной заглушки подтверждает доступ к её БД.
7. Ключ backend принимается внутренним API заглушки. Проверяется чтение случайного отсутствующего платежа, финансовые операции не создаются.

Команда не применяет миграции, не выполняет seed, не создаёт сессии входа и не изменяет финансовые записи. Для БД используются транзакции только на чтение. Проверка наличия активного тура не гарантирует соответствие фильтрам: перед показом проверьте нужное предложение в интерфейсе.

Для нативного запуска PostgreSQL/backend/stubs/nginx: настройте `.env` по [инструкции backend](../backend/README.md), затем выполните `uv run --directory backend python -m app.preflight`. Он использует PUBLIC_APP_URL и PAYMENT_STUB_URL из настроек. Если интерфейс запущен Vite на 5173, укажите `--web-url http://localhost:5173`.

## Повторяемые данные для показа

Каталог содержит «Учебный тур: море в Сочи»: 01–08.06.2027, два туриста, общая цена 100 000 ₽. Для ручного сценария создайте отдельного вымышленного клиента с email в домене example.com, заявку на Сочи с этими датами и бюджетом 120 000 ₽. Туристы и номера документов должны быть заведомо вымышленными. Клиенты, заявки, брони и финансовые операции создаются через обычный сценарий; preflight не подставляет готовые денежные статусы.

Порядок показа и ожидаемые суммы:

1. Менеджер: клиент → заявка → подборка → публичная страница → выбор тура → форма двух туристов → подтверждение поставщика.
2. Два тестовых платежа: 30 000 ₽ и 70 000 ₽. Проверить оплату 100 000 ₽, резерв 0 ₽, остаток 0 ₽ и два уведомления. Реальные деньги и данные карт не используются.
3. Запись общения, поиск клиента; перезапуск `docker compose restart backend stubs`, затем повторная проверка суммы и истории.
4. Отмена: просьба клиента → подтверждение поставщика. Оплата остаётся 100 000 ₽, возврат не происходит автоматически.
5. После подключения экранов #35/#17/#36: отдельно возвраты, переназначение, сверка отчёта и финансовая роль бухгалтера. До этого не заявлять полный сквозной показ этих частей.

Команда preflight проверена на нативном Windows-стенде PostgreSQL/backend/stubs/nginx и автоматическими тестами PostgreSQL. Контейнерные команды приведены по текущему compose.yaml; чистый контейнерный запуск остаётся непроверенным в #24. Ограничения интерфейса и список оставшихся ручных проверок — в [test-report.md](test-report.md).
