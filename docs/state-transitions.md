# Переходы статусов

Версия 0.1 от 15.11.2026. Проект по #6, вместе с [моделью данных](data-model.md). Статусы — отдельные поля заявки, брони, платежа и возврата. Любой неуказанный переход отклоняется. Текущая роль и принадлежность заявки проверяются сервером при каждой команде.

## Общие правила

- «Сотрудник» ниже — ответственный менеджер либо руководитель. Бухгалтер имеет только чтение финансовых данных. Клиент не меняет статусы CRM напрямую.
- Статусы не изменяются произвольным PATCH: сотрудник отправляет бизнес-команду, сервер проверяет условия и атомарно меняет связанные записи. Конкретные маршруты будут согласованы в #7.
- Повтор бизнес-команды с тем же ключом возвращает результат исходной операции. Повтор внешнего результата не меняет суммы, даты первого успеха и уведомления. Противоречивый конечный результат отправляется на сверку, а не переписывает успешную операцию.
- Сетевой тайм-аут — причина ожидания, не переход в failed. Ошибка валидации — 422; конфликт версии/перехода/повторного ключа с другим телом — 409; отсутствие прав — 403. Для недоступного ресурса допустим единый 404, чтобы не раскрывать чужие идентификаторы.

## Заявка

| Значение | Подпись |
|---|---|
| `new` | Новая |
| `in_progress` | В работе |
| `offer_prepared` | Предложение подготовлено |
| `booked` | Забронирована |
| `completed` | Завершена |
| `cancelled` | Отменена |

| Из | В | Команда и условия | Кто |
|---|---|---|---|
| — | `new` | Создать заявку: клиент доступен, назначен ответственный, поля корректны | Сотрудник |
| `new` | `in_progress` | Взять в работу | Сотрудник |
| `in_progress` | `offer_prepared` | Опубликовать подборку из >= 1 тура | Сотрудник |
| `offer_prepared` | `in_progress` | Вернуться к подбору; действующей брони нет; старый выбор сбрасывается, ссылки старых подборок отзываются | Сотрудник |
| `offer_prepared` | `booked` | Подтвердить бронь; выполнены условия подтверждения ниже | Сервер в команде сотрудника |
| `booked` | `completed` | Завершить после `ends_on` по Москве; бронь confirmed, полная успешная оплата, нет pending платежей и возвратов, возвратов не было | Сотрудник |
| `new`, `in_progress`, `offer_prepared` | `cancelled` | Закрыть заявку по просьбе клиента; нет действующей брони | Сотрудник |
| `booked` | `in_progress` | Поставщик подтвердил отмену; у брони нет успешных и pending платежей; выбор сбрасывается, старые ссылки отзываются | Сервер в команде сотрудника |
| `booked` | `cancelled` | Поставщик подтвердил отмену оплаченной брони; pending платежей нет; возврат оформляется отдельно | Сервер в команде сотрудника |

При отказе поставщика заявка остаётся `offer_prepared`; можно выбрать другой тур или вернуться в работу. Создание pending-брони не означает `booked`. Во время отмены заявка остаётся `booked`. У `completed` и `cancelled` нет ручного возврата в работу; для нового обращения создаётся новая заявка. Возврат денег не меняет статус отменённой заявки. Переход оплаченной отмены в `cancelled` — предлагаемое уточнение ТЗ для #6/#7.

## Бронь

| Значение | Подпись |
|---|---|
| `pending_confirmation` | Ожидает подтверждения |
| `confirmed` | Подтверждена |
| `rejected` | Отказ поставщика |
| `cancellation_requested` | Отмена запрошена |
| `cancelled` | Отменена |

| Из | В | Условия | Кто |
|---|---|---|---|
| — | `pending_confirmation` | Заявка offer_prepared, выбран элемент её подборки, нет действующей брони; снимок и сумма сохранены | Сотрудник |
| `pending_confirmation` | `confirmed` | Есть положительный ответ поставщика и номер брони; корректные туристы, количество совпадает со снимком и заявкой; в одной транзакции создаются снимки туристов, confirmed_at и статус заявки booked | Сотрудник |
| `pending_confirmation` | `rejected` | Внесён отказ поставщика с причиной | Сотрудник |
| `confirmed` | `cancellation_requested` | Записана просьба клиента с причиной; заявка ещё не completed | Сотрудник |
| `cancellation_requested` | `cancelled` | Внесено подтверждение отмены поставщиком; pending платежей нет; cancelled_at устанавливается, заявка меняется по таблице выше | Сотрудник |
| `cancellation_requested` | `confirmed` | Поставщик отказал в отмене; ответ с причиной сохранён | Сотрудник |

При отсутствии ответа статус сохраняется. Pending-бронь нельзя просто удалить или превратить в отменённую без выяснения результата поставщика. `rejected` и `cancelled` — конечные статусы попытки; следующая бронь — новая запись. Для новой попытки по существующей заявке сотрудник проходит подбор повторно; у оплаченной отмены создаётся новая заявка.

## Платёж

| Из | В | Условия | Кто |
|---|---|---|---|
| — | `pending` | Бронь confirmed; сумма > 0 и <= available_payment_amount; операция и резерв записаны до HTTP-запроса | Сотрудник через адаптер |
| `pending` | `succeeded` | Подтверждённый ответ сервиса, номер/сумма/валюта совпадают; фиксируются succeeded_at, аудит, уведомления каждому получателю | Адаптер/обработчик результата |
| `pending` | `failed` | Сервис подтвердил окончательный отказ; записана причина, резерв освобождён | Адаптер/обработчик результата |

Подписи: pending — «Ожидает», succeeded — «Успешно», failed — «Ошибка». Тайм-аут оставляет pending, показывается отдельная причина ожидания и выполняется сверка. Даже после запроса отмены ранее созданный pending-платёж может завершиться; новый платёж при этом создавать нельзя. После succeeded/failed статус не редактируется сотрудником. Кнопка повторной попытки создаёт новый платёж только после окончательного failed предыдущего либо в пределах незарезервированного остатка.

## Возврат

| Из | В | Условия | Кто |
|---|---|---|---|
| — | `processing` | Бронь cancelled; исходный платёж succeeded; сумма > 0 и <= доступного остатка этого платежа с учётом processing возвратов; резерв сохранён | Сотрудник через адаптер |
| `processing` | `succeeded` | Сервис подтвердил возврат, номер/сумма/валюта совпадают; succeeded_at и аудит сохранены | Адаптер/обработчик результата |
| `processing` | `failed` | Окончательный отказ сервиса; причина записана, резерв освобождён | Адаптер/обработчик результата |

Подписи: processing — «В обработке», succeeded — «Выполнен», failed — «Ошибка». Тайм-аут сохраняет processing. Сотрудник и бухгалтер не могут вручную отметить успешный возврат. Повтор после окончательного отказа — новая запись. Возврат несколькими частями разрешён; сумма всех успешных возвратов не превышает успешную оплату.

## Отдельные действия без смены статуса

| Действие | Условия и эффект |
|---|---|
| Переназначение заявки | Только руководитель, новый ответственный manager/head; запись аудита в той же транзакции; права пересчитываются |
| Выбор тура | Только сотрудник, только элемент подборки этой заявки, нет действующей брони; выбор не создаёт бронь и не подтверждает оплату |
| Публикация новой подборки | В состоянии offer_prepared можно опубликовать замену при отсутствии действующей брони; старые ссылки отзываются, выбор сбрасывается |
| Изменение пожеланий/дат/количества | В new/in_progress; если предложение подготовлено, сначала возврат в работу. После действующей брони эти поля и снимки не меняются |
| Данные туристов | До создания действующей брони; полная замена списка с ключом повтора и ожидаемой версией заявки; при брони форма только сообщает о закрытии |
| Прочтение уведомления | Только получатель, повторная отметка не создаёт нового уведомления |

Руководитель не обходит финансовые ограничения и условия переходов. Тесты #9–#35 должны проверять допустимые и запрещённые переходы, повторные и параллельные операции; #19 выполняет итоговый сквозной сценарий из всех десяти шагов ТЗ.
