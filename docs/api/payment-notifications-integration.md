# Результаты оплаты, уведомления и завершение — #33

Реализованы list_notifications, read_notification, list_financial_bookings и complete_request. Формы DTO и примеры находятся в openapi.json. Оплата учитывается независимо от открытой карточки; интерфейс только отображает подтверждённое сервером состояние.

## Уведомления

GET /api/notifications доступен manager/head и возвращает NotificationPage. Параметры: page, page_size, sort=-created_at, unread_only=false. Порядок стабилен по created_at/id. unread_count — число всех собственных непрочитанных уведомлений, независимо от страницы и фильтра. total учитывает unread_only. Опрос при активной вкладке — раз в 15 секунд.

POST /api/notifications/{notification_id}/read возвращает Notification. Тела, version и Idempotency-Key нет: повтор сохраняет первое read_at. Чужое уведомление и отсутствующее дают одинаковый 404; руководитель также читает и отмечает только собственные уведомления. Бухгалтер получает 403.

При успехе платежа уведомление получают текущий ответственный и каждый активный руководитель. Повторы внешнего результата не создают новые записи. После переназначения историческое уведомление остаётся у прежнего получателя, но request_id=null и can_open_request=false: скрыть ссылку на заявку. Не строить ссылку по payment_id. Ответ содержит сумму и валюту, без контактов и документов.

## Финансовые брони

GET /api/financial-bookings доступен head/accountant; manager получает 403. Параметры: request_id, status, page, page_size, sort=-created_at. Использовать FinancialBookingPage: суммы строками, paid_amount по succeeded, reserved_payment_amount по pending, remaining_amount=total_amount-paid_amount. Пока возвраты не реализованы, refunded_amount="0.00".

Это отдельное безопасное представление без клиента, снимка тура и паспортов. can_open_request=true только у руководителя; бухгалтер не получает доступ к полной Booking или Request. Для карточек менеджера остаются обычные брони собственной заявки. Списки считают суммы пакетно и не вызывают провайдера для каждой строки.

## Завершение заявки

POST /api/requests/{request_id}/actions/complete принимает ExpectedVersion с version заявки и обязательный Idempotency-Key UUID; возвращает 200 Request. Доступ — текущий ответственный или руководитель. Показывать кнопку только при complete в Request.allowed_actions; перечитывать заявку после результата оплаты и при наступлении следующего дня.

Условия: заявка booked, её действующая бронь confirmed и соответствует выбранному предложению, paid_amount=total_amount, pending-платежей нет. По Москве уже наступил день после Booking.offer_snapshot.ends_on. Именно неизменяемая дата забронированного тура определяет окончание поездки; Request.ends_on хранит пожелание и может отличаться. В последний день тура завершение запрещено.

Команда атомарно сохраняет completed, completed_at, историю и повышение version заявки; версия брони не меняется. Повтор того же тела/ключа безопасен, другое тело даёт idempotency_conflict. Новая команда с устаревшей версией — version_conflict; невыполненные условия — invalid_transition. После 409 перечитать Request. completed — конечный статус, форма туристов закрыта. Модуль возвратов #35 должен дополнить эту проверку запретом завершения после возврата или при ожидающем возврате.

## Доставка и восстановление

Заглушка хранит очередь конечных результатов в PostgreSQL и отправляет каждый результат дважды в POST /internal/payment-events. Это внутренний маршрут, исключённый из клиентского OpenAPI и не опубликованный nginx. Авторизация — Authorization: Bearer PAYMENT_STUB_KEY, не JWT сотрудника. JSON соответствует ответу /v1/payments: id, client_operation_id, amount, currency, status (только succeeded/failed), checkout_token, failure_reason, succeeded_at. Формат проверяется схемой адаптера; CRM сверяет постоянный ключ платежа, внешний ID, сумму и валюту. Успех возвращает 204. Секрет и токен не передавать в клиент, аудит или журналы.

Очередь очищается после двух успешных ответов; сетевые ошибки сохраняют доставку для повтора и после рестарта. Повтор конечного выбора на странице заглушки также возобновляет доставку. Независимая фоновая сверка backend восстанавливает pending, включая потерю ответа при создании операции. Оба обработчика используют обычную транзакционную проверку: суммы, аудит и уведомления фиксируются один раз. Тайм-аут сохраняет резерв. GET карточки и ручной reconcile остаются дополнительными способами сверки.

Планирование обоих обработчиков хранится в БД; FOR UPDATE SKIP LOCKED распределяет задания между процессами. HTTP выполняется вне транзакции. Падение процесса оставляет задание доступным после истечения назначенной задержки.

## Настройка и миграции

Для существующего .env выполнить `python scripts/init_env.py --add-payment-settings`: команда дополняет настройки без замены текущих секретов. Compose включает PAYMENT_RECONCILIATION_ENABLED=true у backend и PAYMENT_CALLBACK_URL=http://backend:8000/internal/payment-events у stubs. При нативном запуске callback по умолчанию настроен на http://localhost:8000/internal/payment-events. Без callback заглушка сохраняет результаты, а backend может получать их сверкой.

Backend: PAYMENT_RECONCILIATION_ENABLED (по умолчанию false без настройки окружения), PAYMENT_RECONCILIATION_INTERVAL_SECONDS=5, PAYMENT_RECONCILIATION_BATCH_SIZE=20. Stubs: STUB_DELIVERY_INTERVAL_SECONDS=1 и STUB_CALLBACK_TIMEOUT_SECONDS=1. Обе стороны используют прежний PAYMENT_STUB_KEY. Фоновая обработка стартует и останавливается вместе с приложением.

CRM Alembic 0010_reconciliation добавляет next_reconcile_at и индекс pending-платежей. Независимая миграция заглушки 0002_delivery добавляет delivery_pending/next_delivery_at и ставит прежние конечные операции в очередь. Обе цепочки применяются при обычном запуске соответствующего сервиса; ручное изменение таблиц не требуется.
