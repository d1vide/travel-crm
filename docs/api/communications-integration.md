# Подключение истории общения — #16

Реализованы три операции из OpenAPI: GET/POST /api/clients/{client_id}/communications и GET /api/requests/{request_id}/communications. Типы — Communication, CommunicationCreate и CommunicationPage. Это записи сотрудника о состоявшемся контакте; отправки email, сообщений или звонков из CRM нет.

## Добавление

POST /api/clients/{client_id}/communications принимает обязательные поля:

| Поле | Значение |
|---|---|
| request_id | UUID доступной заявки этого клиента либо null для общей записи |
| channel | phone, email, messenger, office или other |
| text | Непустая строка; крайние пробелы очищаются, внутренние переносы строк сохраняются |
| occurred_at | Время контакта в UTC с Z: например 2026-11-15T09:00:00Z |

Для записи из карточки заявки используется тот же POST: client_id берётся из Request, request_id заполняется её UUID. Отдельного POST на /requests/{request_id}/communications в контракте нет.

Передавать Idempotency-Key UUID: один ключ на команду, тот же при сетевом повторе и повторе после refresh. Новое или изменённое тело получает новый ключ. Успех — 201 с Communication. Повтор не создаёт вторую запись; другой body с использованным ключом — 409 idempotency_conflict. Одинаковый текст с разными ключами считается разными контактами. Неуспешная команда не сохраняет ключ.

id, client_id, author_id, author и created_at устанавливает сервер; не отправлять их в теле. created_at — время регистрации, occurred_at — время самого контакта, указанное сотрудником. Ввод местного времени преобразовать в UTC перед отправкой; строки без зоны, с +03:00 или +00:00, Unix-числа и некорректные даты отклоняются с 422. Автор ответа уже содержит id/full_name/role, отдельный запрос за именем не нужен.

## Ленты и доступ

Обе ленты возвращают {items, page, page_size, total}. Параметры: page с 1 (максимум 2147483647), page_size 1–100 (по умолчанию 20), sort=-occurred_at. При равном времени сортировка по id по убыванию. Пустой список и страница за пределами списка — 200 с items=[]. Неизвестные параметры и сортировки дают 422.

- В карточке клиента менеджер получает общие записи (request_id=null) и записи своих текущих заявок. Записи чужой заявки исключаются до total и пагинации, даже если сам клиент доступен.
- В карточке заявки выдаются только связанные с ней записи. Общие записи клиента в эту ленту не добавляются.
- Руководитель видит все записи. Бухгалтер получает 403; без входа — 401.
- Недоступный и отсутствующий клиент/заявка дают одинаковый 404. Доступная заявка другого клиента в теле POST — 422; скрытая заявка — 404.
- После переназначения доступ пересчитывается по текущему ответственному. Прежний менеджер теряет доступ к записям этой заявки, даже если у него осталась другая заявка того же клиента. Это действует и на повтор ранее выполненной команды; при утрате доступа повтор даёт 404.
- Автор сохраняется при переназначении и деактивации его учётной записи. Имя и роль в author берутся из текущей безопасной карточки сотрудника, без email, хешей и других внутренних полей.

Обновления и удаления записей через HTTP нет. Создание записи не повышает version клиента или заявки: после успеха достаточно обновить соответствующие ленты. Не смешивать общение с технической историей /requests/{request_id}/history.

## Хранение

Миграция 0005_communications создаёт communications и уникальную пару requests(id, client_id) для составного FK. База отвергает привязку записи к заявке другого клиента. Внешние ключи используют RESTRICT; текст, канал, даты и автор обязательны, request_id может быть null. Индексы client_id/occurred_at/id и request_id/occurred_at/id поддерживают ленты.

Запись и ключ повтора сохраняются в одной транзакции. Порядок блокировок согласован с переназначением: ключ повтора → Client → Request, если заявка указана. Проверки доступа выполняются до повтора и повторно под блокировками. Сервер не хранит дополнительную копию текста в записи идемпотентности.
