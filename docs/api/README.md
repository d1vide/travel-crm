# Основа контракта для фронтенда и бэкенда

Версия 0.1 от 15.11.2026. Проект по #6 для согласования в #7. Здесь закрепляются предлагаемые модели обмена; это не готовый HTTP API и не замена будущего `openapi.json`.

## С чего начать

1. Прочитать [актуальное ТЗ](../technical-specification.md), [модель данных](../data-model.md) и [переходы статусов](../state-transitions.md).
2. Использовать [domain.schema.json](domain.schema.json) как машиночитаемый словарь DTO и enum. В нём JSON Schema Draft 2020-12; конкретная модель выбирается ссылкой `domain.schema.json#/$defs/Request`, аналогично для остальных `$defs`.
3. Для моков и форм взять [domain.examples.json](domain.examples.json). Каждый элемент содержит имя схемы и отдельный пример. Примеры разных сущностей независимы: это не связанный seed БД и не ответ реализованного сервера.
4. В #7 согласовать маршруты, параметры фильтров, пагинацию, тела команд, ошибки, доступ и предложения из раздела «Уточнения для согласования» модели данных. Охват — FR-01…FR-13, включая публичные страницы и возвраты.
5. В #26 экспортировать OpenAPI из Pydantic и генерировать TypeScript-клиент/типы из него. При переносе сверить имена, nullable, деньги и enum с этой схемой. После переноса источником HTTP-контракта становятся Pydantic и экспортированный `openapi.json`; не поддерживать два независимых противоречащих контракта.

## Правила обмена

| Область | Соглашение |
|---|---|
| Поля JSON | `snake_case`; внутри Vue допускается явное преобразование в camelCase на границе API |
| UUID | Строки, без преобразования в number |
| Деньги | Строки с двумя знаками: `"100000.00"`, валюта `RUB`; вычисленные остатки приходят с сервера |
| Время | RFC 3339 UTC с `Z`; отображение Europe/Moscow; календарные даты `YYYY-MM-DD` |
| Отсутствующее значение | `null` для явно nullable поля; read DTO содержит все required поля |
| Роли | `manager`, `head`, `accountant` — совпадают с существующим фронтендом |
| Авторизация | Ответ `AuthResult`: `access_token`, `user.id`, `user.full_name`, `user.role`; refresh только в HttpOnly cookie |
| Ошибка | `Error`: `{code, message, fields: [{field, message}]}`; сообщение по-русски, field — путь поля JSON, например `tourists.0.birth_date` |
| Повтор команды | Предлагаемый заголовок `Idempotency-Key` для создания заявки/брони/платежа/возврата и отправки туристов; тот же ключ используется только для повтора того же тела |
| Конкурентное редактирование | Поле `version` в read DTO; ожидаемая версия передаётся в теле команды. Форма туристов использует `request_version`. При 409 перечитать ресурс и показать конфликт |
| Условия переходов | Матрица переходов — в state-transitions.md; схема содержит `x-state-transitions` со списком рёбер. Ребро не означает, что операция доступна без проверки условий |

JSON Schema проверяет форму одного DTO, но не права, связи с БД, календарную корректность интервалов, суммы нескольких операций и условия статусов. `format` должен проверяться валидатором явно. Эти правила остаются серверной логикой и интеграционными проверками.

Проверка схемы и всех примеров из корня репозитория (Python 3.12+ и uv; зависимость закреплена внутри скрипта):

```bash
uv run docs/api/validate_contract.py
```

Если Python и jsonschema 4.26.0 уже установлены, достаточно `python docs/api/validate_contract.py`. Проверка не подключается к API и не подтверждает выполнение бизнес-правил сервером.

## Модели и экраны

| Экран/операция | Схемы | Что учитывать |
|---|---|---|
| Сессия | `User`, `AuthResult`, `Role` | Не сохранять access в localStorage; пароли и refresh не входят в DTO |
| Клиенты | `Client` | Контакт обязателен; уникальный номер не равен UUID; совпадение контактов не означает автоматическое слияние |
| Заявки | `Request`, `RequestStatus` | Поле selected_selection_item_id указывает на снимок конкретной подборки; статус меняется бизнес-командой |
| Каталог | `TourOffer`, `OfferSnapshot` | Цена общая на tourist_count туристов; zero допустим для тестового предложения, отрицательная цена нет |
| Подборка сотрудника | `Selection`, `SelectionItem` | request_id доступен только сотруднику; создание и выбор — отдельные команды |
| Публичная подборка | `PublicSelection` | Только снимки туров и срок ссылки; нет клиента, manager_id, паспортов, остальных подборок |
| Туристы сотрудника | `Tourist`, `TouristSnapshot` | Только ответственный/руководитель; при подтверждении брони сохраняется отдельный снимок |
| Публичная форма туристов | `PublicTouristForm`, `TouristSubmission`, `TouristSubmissionResult` | GET не возвращает ранее введённые паспорта; новые элементы с id=null; известные id разрешены только своей заявке; отправляется полный список |
| Бронь | `Booking`, `BookingStatus` | Отдельные сумма успешных оплат, резерв, остаток долга, доступная новая оплата и возвраты; при pending остаток долга не равен сумме нового платежа |
| Деньги/бухгалтер | `Payment`, `Refund` | Финансовые DTO не содержат персональные карточки; выбранный платёж указывается при возврате. Сводка брони для бухгалтера проектируется отдельно в #7, полный Booking ему не отдаётся |
| Общение | `Communication` | occurred_at — фактическое время контакта, created_at — время серверной записи; request_id nullable |
| Уведомления | `Notification` | Уникальность на платёж и получателя; свои read_at; без раскрытия чужой заявки |
| Выдача ссылки сотруднику | `PublicLink` | Сырой токен только в созданной url, в БД хеш; повторное копирование после потери url требует перевыпуска с отзывом старой |
| Отчёт | `Report` | Даты включительно по Москве, оплаты и возвраты отдельными суммами; только руководитель |

Поля для создания/изменения не копируются автоматически из read DTO: `id`, автор, денежные итоги, системные даты и статусы клиент не назначает. `TouristSubmission` — специально выделенная входная модель публичной формы. Остальные входные модели и HTTP-маршруты ещё не согласованы в #7. Не подключать UI к выдуманным адресам по имени DTO.

## Согласование с фронтендом

После чтения PR по #6 фронтенд проверяет:

- [ ] Данных достаточно для списка и карточки клиента, заявки, каталога и подборки.
- [ ] Формы принимают строковые деньги, nullable и даты без потери часового пояса.
- [ ] Отдельные статусы и остатки позволяют показать частичную оплату, ожидание, отмену и возврат.
- [ ] Публичные страницы используют ограниченные DTO, а не полную карточку CRM.
- [ ] Подтверждены либо скорректированы предложения: поля туристов, срок ссылок, доступ к клиенту без заявки, версии, резервы и отмена оплаченной брони.

Подтверждение фиксируется в #6/PR. До него задача не считается согласованной. Изменение модели сопровождается обновлением схемы, примеров и описания; несовместимые изменения явно отмечаются в PR.
