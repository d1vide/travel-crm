# Профиль сотрудника — #48

`GET /api/auth/me` реализован для всех трёх ролей и возвращает `UserProfile`: `id`, `full_name`, `role`, `email`, `department`, `position`, `work_phone`. Требуется access-токен; ответ `Cache-Control: no-store`. Профиль относится только к вошедшему сотруднику, параметра чужого пользователя нет. Изменение профиля через API в текущий объём не входит.

`email` — существующий адрес учётной записи. Остальные три поля всегда присутствуют: строка либо `null`, если не заполнены. Ограничения длины: отдел и должность — 255, телефон — 64, email — 320 символов. Телефон — отображаемая рабочая строка, не нормализованный контакт клиента.

Экран `/profile` и адаптер `frontend/src/api/profile.ts` уже читают эти snake_case-поля и показывают прочерк при `null`. Дополнительный запрос или изменение формы не нужны. Схема `User` в login/refresh, списке ответственных, авторах и бизнес-карточках сохраняет только `id`, `full_name`, `role`.

Миграция `0012_employee_profile` добавляет три nullable-колонки без изменения существующих записей. Старые сотрудники после обновления получают `null`; seed не перезаписывает их профиль, пароль, роль или контакты. При создании новых демо-сотрудников seed заполняет учебные отделы/должности и заведомо вымышленные рабочие телефоны. Для существующей демо-БД значения заполняются отдельно администратором; сбрасывать БД ради отображения профиля не требуется.

Полная спецификация — `docs/api/openapi.json`, примеры — `domain.examples.json`. Операция остаётся `x-implementation-status=implemented`; её идентификатор `get_current_user` и URL сохранены.
