# Подключение оплаты — #15

Реализованы пять операций OpenAPI: создание платежа, список платежей брони, глобальный финансовый список, карточка и сверка. Использовать Payment, PaymentPage и PaymentCreate. Финансовая сводка броней, API уведомлений и complete реализованы в #33: [подключение](payment-notifications-integration.md). Возвраты реализованы в [#35](refunds-integration.md).

## Создание и платёжная ссылка

POST /api/bookings/{booking_id}/payments принимает version самой брони, amount строкой с двумя знаками и currency=RUB. Сумма строго положительная и не больше Booking.available_payment_amount. Входные данные карты и неизвестные поля запрещены. Только manager/head с текущим доступом к заявке могут создавать платёж; бронь должна быть confirmed.

Обязателен Idempotency-Key UUID. Сетевой повтор и повтор после refresh сохраняют исходные тело и ключ. Повтор возвращает тот же платёж в текущем разрешённом состоянии, даже если версия брони уже изменилась. Другое тело с тем же ключом — 409 idempotency_conflict. Новая команда со старой версией — 409 version_conflict; превышение доступного остатка — 409 payment_limit_exceeded. После утраты доступа повтор даёт 404.

Ответ всегда 202 с текущим Payment, а не подтверждение успеха оплаты. Сначала сервер фиксирует pending-платёж, резерв, повышение version брони и ключ повтора; затем вызывает заглушку без удержания транзакции. При потере ответа или недоступности сервиса платёж остаётся pending, payment_url/external_operation_id могут быть null, pending_reason объясняет ожидание. Повтор или сверка восстанавливают ту же внешнюю операцию по постоянному ключу Payment.id.

Если payment_url не null, копировать ровно этот адрес. Он строится из PUBLIC_APP_URL и проверенного токена заглушки; Host запроса и произвольный URL из внешнего ответа не используются. Страница /payment-stub/pay/:token открывается без JWT и содержит только сумму и выбор учебного исхода «Успех», «Отказ», «Тайм-аут». Реальные деньги и данные банковских карт не используются. Токен ссылки не сохранять в аналитике и журналах.

## Состояние, сверка и суммы

GET /api/payments/{payment_id} возвращает 200 Payment. Для pending он сверяет существующую операцию через серверный адаптер; открытый pending-платёж можно опрашивать раз в 5 секунд. GET не создаёт новый локальный платёж или новый резерв. POST /api/payments/{payment_id}/reconcile — естественно повторяемая команда без тела и ключа повтора, возвращает 202. Бухгалтер имеет только GET; POST ему запрещён.

Тайм-аут не означает failed и не освобождает резерв. В заглушке после выбора тайм-аута запрос статуса действительно задерживается дольше тайм-аута адаптера; ссылка остаётся открытой, позднее можно выбрать окончательный успех/отказ. После выбора исхода перечитать Payment, Booking и Request. Переход браузера или ответ страницы заглушки сами по себе не подтверждают оплату: CRM принимает только проверенный HTTP-результат сервиса через адаптер или внутреннюю доставку.

Сервер сопоставляет внешний ID, постоянный ключ операции, сумму и валюту. Успех/отказ учитываются один раз; терминальный статус и succeeded_at не переписываются повтором. Устаревший pending-ответ после успеха игнорируется. Противоречивый конечный результат не меняет суммы и фиксируется в аудите для сверки. Не отправлять ручные поля status или succeeded_at в CRM.

Booking.paid_amount — сумма succeeded; reserved_payment_amount — сумма pending; remaining_amount=total_amount-paid_amount; available_payment_amount=total_amount-paid_amount-reserved_payment_amount, только для confirmed. Pending уже резервирует деньги. Несколько частичных платежей допустимы в пределах незарезервированного остатка. После failed резерв освобождается, повторная попытка создаётся отдельным платежом с новым ключом и актуальной версией брони. Возвраты #35 подключены: refunded_amount и reserved_refund_amount отражают succeeded/processing, available_refund_amount учитывает оба значения и доступен только для succeeded по cancelled-брони. create_refund определяется ролью и доступным остатком.

Создание резерва и каждый переход pending → succeeded/failed повышают version брони. Выдача ссылки и повтор того же результата не повышают её. Версия заявки при денежной операции не меняется, но проекция Request.active_booking получает актуальные оплаченные суммы; перечитывать её после результата. create_payment в Booking.allowed_actions предлагается только для confirmed с положительным доступным остатком.

## Списки, права и уведомления

GET /api/bookings/{booking_id}/payments — manager/head, доступ по текущей заявке. Параметры page/page_size и sort=-created_at. GET /api/payments — только head/accountant: request_id, booking_id, status, page/page_size, sort=-created_at/created_at. Фильтры объединяются AND; порядок стабилен по created_at/id. Списки читают локальные состояния и не выполняют сетевой опрос для каждой строки. Для ожидающих записей опрашивать карточку платежа.

Payment не содержит контакты клиента или документы туристов. can_open_request=false и allowed_actions=[] для бухгалтера; менеджер получает только свои текущие заявки. Чужой и отсутствующий платёж дают одинаковый 404. Ответы защищены no-store/no-referrer.

При успехе статус, сумма, аудит и по одной записи notifications на текущего ответственного и каждого активного руководителя фиксируются вместе; получатели без повторов. Переназначение во время HTTP-вызова не теряет результат: сервер сохраняет подтверждённый факт и уведомляет текущих получателей, а прежнему менеджеру возвращает 404. API индикатора/списка/прочтения уведомлений, завершение заявки и финансовая сводка реализованы в [#33](payment-notifications-integration.md); отмена реализована в [#34](booking-cancellation-integration.md), возврат реализован в [#35](refunds-integration.md). Эти задачи не закрываются по готовности оплаты.

## Запуск и протокол заглушки

Для нового окружения: python scripts/init_env.py, затем docker compose up --build. Для существующего .env: python scripts/init_env.py --add-payment-settings добавляет недостающие настройки сервиса, фоновой сверки и callback, не заменяя прежние значения. Ключ хранится только в локальном .env; его нельзя помещать в VITE_* или клиентский код. По умолчанию PUBLIC_APP_URL=http://localhost:8080. Для Vite установить origin своего dev-сервера и при необходимости VITE_PAYMENT_STUB_TARGET (по умолчанию http://localhost:8010).

Compose содержит db, stubs, backend, web. Заглушка доступна напрямую только на 127.0.0.1:8010 (PAYMENT_STUB_PORT), браузер открывает её через nginx/Vite на том же origin. Внутренний PAYMENT_STUB_URL=http://stubs:8010. У stubs собственная схема PostgreSQL payment_stub, собственные миграции Alembic и постоянные операции; рестарт не очищает состояния. При нативном запуске из корня: backend/.venv/Scripts/python.exe -m stubs.bootstrap, затем backend по его README. Для Linux путь к Python — backend/.venv/bin/python.

Внутренний POST /v1/payments принимает client_operation_id (UUID Payment.id), amount и currency; повтор с тем же ключом возвращает ту же операцию, другое тело — 409. GET /v1/payments/{id} возвращает id, client_operation_id, amount, currency, status, checkout_token, failure_reason, succeeded_at. Оба маршрута требуют Authorization: Bearer PAYMENT_STUB_KEY; nginx их не публикует. Сырой checkout-токен восстанавливается HMAC от постоянного ключа операции, в БД заглушки только его хеш. CRM хранит выданный payment_url в платеже, без копирования в аудит и результат идемпотентности. Общий секрет должен оставаться постоянным при перезапуске; его смена требует отдельного переноса активных тестовых ссылок.

Миграция CRM 0009_payments добавляет payments и notifications. Внешний ID уникален в пределах provider, сумма положительная, терминальные поля проверяются БД. Проверка доступного остатка и результат сериализуются под Client → Request → Booking → Payment; сетевой вызов выполняется между транзакциями. Суммы для списков заявок и броней собираются пакетно. В public URL нет номера брони, контактов или JWT. nginx и заглушка не записывают платёжные токены в access/error журналы.
