# Сводный отчёт — #36

GET /api/reports/summary?date_from=2026-11-01&date_to=2026-11-30 реализован и доступен только head. Менеджер и бухгалтер получают 403, без авторизации — 401. Оба параметра обязательны, формат YYYY-MM-DD; date_to >= date_from. Неизвестные параметры и некорректные даты — 422 с общим Error. Однодневный период допустим.

Ответ Report содержит date_from/date_to, timezone="Europe/Moscow", currency="RUB" и четыре показателя:

| Поле | Что считается |
|---|---|
| requests_created | Число заявок по created_at |
| bookings_confirmed | Число попыток бронирования по confirmed_at, включая впоследствии отменённые |
| payments_succeeded_amount | Валовая сумма succeeded-платежей по succeeded_at |
| refunds_succeeded_amount | Сумма succeeded-возвратов по succeeded_at |

Обе календарные границы включаются: от начала date_from до начала дня после date_to в Europe/Moscow. Преобразование выполняет PostgreSQL по правилам часового пояса; часовой пояс браузера и Windows на результат не влияют. Дата создания платежа/возврата не определяет попадание в период. Pending/processing/failed не входят в суммы. Возвраты показываются отдельно, не вычитаются из строки оплат. Одна заявка может дать несколько исторических подтверждений разных броней.

Суммы — строки с двумя знаками. Пустой период возвращает 200, нулевые счётчики и "0.00"; показывать пустой отчёт, не ошибку. Каждая метрика агрегируется отдельно, поэтому туристы/платежи/возвраты не размножают строки; все четыре метрики используют один снимок одного SQL-запроса. Персональных данных в ответе нет. Ответ no-store/no-referrer.

Для экрана использовать get_summary_report и Report из OpenAPI. Не пересчитывать показатели из загруженных страниц списков и не добавлять часовой пояс к датам фильтра. После изменения периода делать новый запрос; сервер проверяет роль независимо от меню. Новая миграция не требуется.
