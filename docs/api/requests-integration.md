# Подключение заявок — #13

В OpenAPI реализованы десять операций: список, создание, карточка, изменение заявки, смена ответственного, start-work, cancel, resume, история заявки и список ответственных. Использовать сгенерированные Request, RequestCreate, RequestUpdate, RequestPage, AssignRequest, ExpectedVersion, ReasonCommand, AuditRecordPage и UserPage.

## Создание и карточка

POST /api/requests принимает обязательные client_id, manager_id (nullable), destination, starts_on, ends_on, tourist_count, budget и wishes. manager_id=null назначает текущего сотрудника. Менеджер может назначить только себя, руководитель — активного manager/head. Клиент должен быть доступен создающему сотруднику. Успех — 201 с Request, статус new и version=1.

GET /api/requests/{request_id} возвращает карточку с краткими client и manager: дополнительные запросы за именами не нужны. budget — строка с двумя десятичными знаками, включая "0.00"; числовой JSON, отрицательные суммы и больше двух знаков отклоняются. Максимум — "999999999999.99". Даты только YYYY-MM-DD, окончание не раньше начала; tourist_count — целое число 1–2147483647, без преобразования строк и boolean. Сервер очищает пробелы вокруг направления, пустое направление запрещено.

Менеджер видит только свои заявки, даже если имеет доступ к клиенту по другой заявке. Руководитель видит все; бухгалтер получает 403. Скрытая и отсутствующая заявка дают одинаковый 404. Авторизация обязательна.

## Списки и ответственные

GET /api/requests поддерживает status, manager_id, client_id, page, page_size и sort. Менеджеру чужой manager_id даёт 403. client_id проверяется на доступность: скрытый/несуществующий клиент даёт 404. Права применяются до total и пагинации. page начинается с 1, максимум 2147483647; page_size 1–100, по умолчанию 20. sort: -created_at (по умолчанию), created_at, starts_on; при равенстве добавляется id в том же направлении. Пустая страница — 200 с items=[]. Неизвестные параметры и значения — 422.

GET /api/users доступен только руководителю и возвращает UserPage активных manager/head, без email и других внутренних полей. sort=full_name; поддерживаются page/page_size. Менеджеру список для создания не нужен: передаётся manager_id=null.

## Изменения и команды

Для каждой записи обязателен Idempotency-Key UUID. При сетевом повторе и после refresh сохранять исходные ключ и тело. Новая команда получает новый ключ. Успешный повтор возвращает текущую доступную карточку без второй записи, изменения версии или аудита. Тот же ключ с другим телом — 409 idempotency_conflict. После утраты доступа повтор даёт 404. Неуспешные команды не запоминаются.

PUT /api/requests/{request_id} принимает RequestUpdate с текущей version. Редактируются направление, даты, количество, бюджет и пожелания; только в new/in_progress. Нельзя менять client_id, manager_id или status через PUT. При 409 version_conflict перечитать карточку и предложить пользователю повторно применить изменения; не повышать версию автоматически.

PATCH /api/requests/{request_id}/assignee принимает AssignRequest (version, manager_id), доступен только head. Новый ответственный должен быть активным manager/head. Реальная смена увеличивает version и создаёт запись аудита в той же транзакции. Назначение того же сотрудника — 200 без повышения version и лишнего аудита. После переназначения прежний менеджер теряет доступ к заявке и истории; доступ к клиенту пересчитывается по всем его заявкам.

Команды возвращают 200 с новой карточкой:

| Маршрут после /api/requests/{request_id}/actions/ | Тело | Переход |
|---|---|---|
| start-work | ExpectedVersion | new → in_progress |
| cancel | ReasonCommand | new/in_progress/offer_prepared → cancelled; обязательная непустая причина |
| return-to-work | ExpectedVersion | offer_prepared → in_progress; выбор очищается, ссылки отзываются |
| resume | ExpectedVersion | cancelled → in_progress; причина и время отмены очищаются, аудит остаётся |

Недопустимый переход — 409 invalid_transition. Удаления нет. allowed_actions содержит только доступные сейчас реализованные действия, включая reassign для руководителя; поля проверяются сервером повторно.

## История

GET /api/requests/{request_id}/history возвращает AuditRecordPage; доступ совпадает с карточкой заявки. Параметры: page/page_size, sort=-created_at. В аудите создания/смены статуса и ответственного есть actor с именем, source=staff, action, changes и created_at. changes содержит только manager_id/request_status с прежним и новым значением. Причина отмены остаётся в карточке, произвольный текст и внутренние поля не попадают в историю. Это технический аудит, история общения подключается отдельно в #16.

Создание заявки блокирует Client до назначения, чтобы права клиента и его изменение оставались согласованными. Аудит и запись повтора коммитятся с бизнес-операцией.
