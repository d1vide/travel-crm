# Проверка совместимости контракта с фронтендом

Дата: 15.11.2026. По поручению владельца проекта сверены ТЗ 0.2, сценарии US-01…US-15 в объёме MVP, карты историй/событий и каркас Vue из main `869fb81`.

Вывод: модель подходит; необходимые для экранов дополнения включены в контракт 0.2. Проверка выполнена по исходникам и сценариям: отсутствующие бизнес-экраны ещё не подключены к работающему серверу. Отдельное ревью Холодкова не заявляется. Контракт зафиксирован как базовая спецификация для обеих частей проекта.

## Исправления модели

1. Для таблиц и выбора ответственного добавлены ClientBrief, Request.manager, Communication.author и users; одних UUID недостаточно.
2. Введён FinancialBooking с суммами/датами/идентификаторами: полный Booking содержит туристов и бухгалтеру недоступен.
3. Добавлены allowed_actions: одна роль или статус не определяют доступность кнопки.
4. Долг, резерв и доступная новая оплата разделены; возврат использует остаток исходного платежа.
5. Pending-бронь закрывает форму: полный список туристов теперь обязателен уже для создания брони, чтобы исключить тупик.
6. Кратность снимков туристов исправлена на 0..N до подтверждения; при confirmed обязательно >=1.
7. Для оплаченной отмены добавлено resume заявки после завершения ожидающих денежных операций. История и деньги прежней брони сохраняются отдельно.
8. Копирование сырой ссылки возможно из ответа, после потери url — явный перевыпуск; автоматические сетевые повторы выдачи не используются при хранении только хеша.

## Изменения, необходимые при подключении фронтенда

- [roles.ts](../../frontend/src/auth/roles.ts), [auth.ts](../../frontend/src/api/auth.ts), [errors.ts](../../frontend/src/api/errors.ts) совместимы с Role, AuthResult и Error; UUID строковые.
- [navigation.ts](../../frontend/src/auth/navigation.ts) уже ограничивает глобальные финансы head/accountant. Менеджер получает их внутри своей заявки.
- [http.ts](../../frontend/src/api/http.ts) пока не принимает заголовки команды. Добавить RequestOptions/адаптер с Idempotency-Key; сохранять ключ при повторе после 401, не создавать его на каждую попытку fetch. Проверить повтор записи с тем же ключом после refresh.
- [guard.ts](../../frontend/src/router/guard.ts) трактует meta.public как страницу только для гостя: сотрудник перенаправляется домой. Отделить guestOnly для входа от общедоступных подборки/формы. Публичные страницы работают и для менеджера, до ensureRestored и вне MainLayout; проверить гостя и сотрудника.
- [MainLayout.vue](../../frontend/src/layouts/MainLayout.vue) очищает только память. В #11 подключить POST auth/logout и затем локальную очистку сессии.
- Деньги вводить строкой либо целыми копейками с явной сериализацией в десятичную строку; не посылать parseFloat как JSON number. Максимум брать с сервера.
- Календарные даты не преобразовывать из локальной полуночи через toISOString: передавать YYYY-MM-DD. События отображать из UTC в Europe/Moscow.
- Новая команда — новый UUID ключа; повтор того же тела — прежний. Изменённое после валидации тело — новый ключ. Пока команда выполняется, форма заблокирована.
- После 409 version_conflict перечитать карточку. После вложенных команд перечитать затронутые Request/Booking; не увеличивать version локально.
- 202, pending/processing и payment_url=null показывают ожидание. Открытые операции опрашиваются раз в 5 секунд, уведомления раз в 15 секунд при активной вкладке. Reconcile не означает ручное подтверждение успеха.
- Публичные страницы используют отдельный fetch без Bearer и без восстановления сессии. Недействительная ссылка — единый экран; закрытая форма — is_editable=false с причиной, без персональных данных.
- Кнопки используют allowed_actions. Статус не редактируется универсальным PUT; read-карточка не копируется в команду целиком.

## Границы проверки

Бизнес-страницы сейчас используют SectionStub, поэтому фактический вид форм и полный работающий сценарий пока не проверяемы. Проверены достаточность данных/операций, существующие имена авторизации/ошибок и пригодность контракта для TypeScript. После реализации нужны интеграционные проверки и десять шагов приёмки ТЗ.

Воспроизводимые проверки: Draft 2020-12, OpenAPI 3.1.1, примеры всех объектов, ссылки, уникальность operationId, права публичных/финансовых операций, синхронизация генератора. Проверка TypeScript на границе подтверждает AuthResult/FieldError, строковые деньги и отсутствие персональных полей в публичных/бухгалтерских DTO.

Фактически выполнено: валидатор проверил 79 определений, 60 примеров и 60 HTTP-операций; отклонены 19 некорректных примеров. OpenAPI преобразован openapi-typescript 7.13.0 в TypeScript; строгая компиляция с реальными AuthResult, Role и FieldError текущего фронтенда прошла. Отрицательные проверки типов подтвердили запрет числовых денег и отсутствие персональных полей в PublicSelection/PublicTouristForm/FinancialBooking. Python-скрипты прошли Ruff.

Prism 5.14.2 запущен по этому OpenAPI: список заявок с именами, публичная подборка и финансовый список ответили 200, создание платежа — 202, заданная контрактная ошибка — 422 с Error; публичный ответ имел Cache-Control: no-store. Пути включают /api явно, поэтому переключение Vite на мок не требует rewrite. Prism проверяет форму обмена, но не реализует x-roles, версии и транзакционные ограничения.
