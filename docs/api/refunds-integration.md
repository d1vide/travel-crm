# Подключение возвратов — #35

Реализованы пять операций: create_refund, list_payment_refunds, list_refunds, get_refund и reconcile_refund. Формы RefundCreate/Refund/RefundPage и примеры находятся в openapi.json. Возврат связан с конкретным исходным платежом и не меняет статус оплаты, отменённой брони или заявки.

## Создание и ограничения

POST /api/payments/{payment_id}/refunds принимает `{amount: "1000.00", currency: "RUB"}` и обязательный Idempotency-Key UUID. **version в этой команде нет**. Доступ — текущий ответственный или руководитель. Бронь должна быть cancelled, платёж succeeded; сумма положительна и не больше Payment.available_refund_amount. Нельзя отправлять статус, внешний номер, дату успеха или тестовый исход.

available_refund_amount = amount исходного платежа − успешные возвраты − processing-резервы; вне cancelled/succeeded он равен "0.00". Выбирать конкретный платёж, а не общий оплаченный остаток брони. При нескольких платежах возврат оформляется отдельно по каждому. Успешные возвраты и processing вместе не могут превысить исходную оплату даже при параллельных командах.

Ответ — **202 с текущим Refund**, который может уже быть succeeded/failed или ещё processing. HTTP 202 сам по себе не подтверждает возврат. Сначала CRM сохраняет processing-операцию, резерв и ключ, затем вызывает сервис вне транзакции. При тайм-ауте сохраняются processing и pending_reason, external_operation_id может быть null. Сервис восстанавливает ту же операцию по постоянному Refund.id, новый резерв при повторе не создаётся.

Сетевой повтор и повтор после refresh сохраняют исходные тело и ключ. Новая попытка после окончательного failed получает новый ключ; повтор старого ключа вернёт прежний failed. Другое тело с тем же ключом — 409 idempotency_conflict, превышение остатка — refund_limit_exceeded, неверное состояние — invalid_transition. После потери доступа повтор тоже запрещён. Ошибки полей — 422.

## Карточки, списки и права

GET /api/refunds/{refund_id} возвращает Refund и для processing сверяет результат через адаптер. Открытую processing-карточку можно опрашивать раз в 5 секунд. POST /api/refunds/{refund_id}/reconcile — повторяемая команда без тела и ключа, ответ 202. Создание и POST сверки разрешены manager/head; accountant имеет только чтение.

GET /api/payments/{payment_id}/refunds доступен manager/head/accountant по правам исходного платежа; параметры page/page_size, sort=-created_at. GET /api/refunds — глобальный список только head/accountant; фильтры request_id, booking_id, payment_id, status, page/page_size, sort=-created_at/created_at объединяются AND. Порядок стабилен по created_at/id; списки читают локальные результаты и не опрашивают провайдера для каждой строки.

Refund содержит идентификаторы и суммы, без контактов, туристов и ссылки оплаты. Для бухгалтера can_open_request=false и allowed_actions=[]; менеджер видит только свои текущие заявки. Чужая и отсутствующая запись дают одинаковый 404. Ответы no-store/no-referrer. Показывать сверку по Refund.allowed_actions, создание возврата — по Payment.allowed_actions.

## Суммы, версии и возобновление

Payment.refunded_amount — сумма succeeded-возвратов этого платежа; reserved_refund_amount — сумма processing; available_refund_amount учитывает оба значения. Booking.refunded_amount и FinancialBooking.refunded_amount агрегируют успешные возвраты всех её платежей. paid_amount остаётся валовой суммой оплат, remaining_amount=total_amount-paid_amount; возврат не создаёт возможность оплатить старую отменённую бронь снова.

Резервирование и каждый конечный результат увеличивают Booking.version по одному разу; повторы и промежуточная выдача внешнего номера её не меняют. Request.version при денежном результате не повышается. После команды/изменения состояния перечитать Payment, Booking, Request и финансовый список. Не вычислять суммы и версии локально.

Processing по любой прежней брони блокирует resume заявки; успех или окончательный отказ снимают этот резерв. Успешный возврат сам не возобновляет заявку. После resume деньги старых попыток остаются у них; возврат по старой отменённой брони разрешён независимо от нового подбора. Завершение проверяет отсутствие processing и успешных возвратов именно действующей брони. Старая отменённая попытка не оплачивает и не блокирует завершение новой.

## Надёжность и запуск

CRM сверяет внешний ID, Refund.id, внешний ID исходного платежа, сумму и валюту. Первый конечный результат и succeeded_at сохраняются; повтор не меняет суммы и историю, противоречие отмечается для сверки. Успешный/ошибочный результат и аудит фиксируются одной транзакцией. Общий порядок блокировок: Client → Request → Booking → Payment → Refund. HTTP выполняется после освобождения транзакции.

Существующий обработчик PAYMENT_RECONCILIATION_ENABLED=true также сверяет processing-возвраты без открытой карточки. Настройки интервала/пакета общие с платежами; расписание next_reconcile_at хранится в PostgreSQL, задания распределяются через SKIP LOCKED и восстанавливаются после перезапуска. Возвраты используют опрос провайдера; платёжный callback #33 остаётся отдельным механизмом.

Миграция CRM 0011_refunds создаёт refunds с ограничениями, индексами и расписанием; миграция заглушки 0003_refunds — независимую refund_operations с FK на её собственный платёж. Применяются обычным запуском сервисов. STUB_REFUND_OUTCOME=succeeded по умолчанию, допустимы failed/timeout; Compose читает это значение из .env. Для нативного запуска используется та же переменная. Новые секреты не требуются.

Внутренний протокол заглушки: POST /v1/refunds принимает client_operation_id (Refund.id), payment_id (внешний ID платежа), amount и currency; GET /v1/refunds/{id} возвращает id, client_operation_id, payment_id, amount, currency, status, failure_reason и succeeded_at. Маршруты требуют Authorization: Bearer PAYMENT_STUB_KEY и не опубликованы nginx. Заглушка самостоятельно проверяет лимит исходной оплаты и постоянство тела повтора. При timeout операция коммитится, но HTTP задерживается дольше тайм-аута адаптера; резерв остаётся. Для позднего результата на тестовом стенде доступен защищённый POST /v1/refunds/{id}/outcome с `{outcome: "succeeded"}` или failed/timeout. Конечный результат переписать нельзя. Этот маршрут предназначен для управления заглушкой, не для интерфейса CRM; общий ключ нельзя помещать в VITE_* или клиентский код.
