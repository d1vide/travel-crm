# Подключение бронирований — #14

Реализованы пять операций OpenAPI: список попыток заявки, создание брони, карточка, подтверждение и отказ поставщика. Использовать Booking, BookingPage, BookingTourist, ExpectedVersion, ConfirmBooking и ReasonCommand. Финансовая сводка и complete реализованы в [#33](payment-notifications-integration.md). Три команды отмены брони реализованы в [#34](booking-cancellation-integration.md).

## Создание и список попыток

POST /api/requests/{request_id}/bookings принимает ExpectedVersion, где version — текущая версия заявки. Выбранный selection_item_id, снимок тура, сумма и валюта берутся сервером из заявки. Клиент не передаёт цену или read DTO. Успех — 201 Booking со статусом pending_confirmation и version=1. Заявка остаётся offer_prepared, но её version увеличивается на 1: после команды перечитать Request.

Условия: заявка offer_prepared, выбран элемент её последней подборки, действующей брони нет, текущий список туристов полный и корректный. Число туристов должно одновременно совпадать с заявкой и выбранным снимком тура. Перед созданием повторно проверяются ФИО, даты рождения, номера документов и обязательный срок загранпаспорта. При невыполнении условий — 409 invalid_transition; версия проверяется отдельно с 409 version_conflict.

Цена фиксируется из SelectionItem.offer_snapshot, а не из текущего каталога. Изменение цены или активности предложения после публикации не переписывает согласованный снимок. total_amount — строка с двумя знаками, валюта RUB; нулевая стоимость допустима. Даты и направление пожеланий заявки не обязаны точно совпадать с выбранным туром; количество обязано.

GET /api/requests/{request_id}/bookings возвращает BookingPage с page/page_size и sort=-created_at. Порядок стабилен по created_at/id; старые отклонённые попытки сохраняются. GET /api/bookings/{booking_id} возвращает Booking. Пустая страница — items=[], пагинация применяется после проверки прав.

Менеджер видит только брони своих текущих заявок, руководитель — всех. Бухгалтер получает 403: Booking содержит документы туристов. Для бухгалтера доступно отдельное финансовое представление GET /api/financial-bookings. Чужая и отсутствующая бронь дают одинаковый 404. Все ответы бронирований защищены no-store/no-referrer; не сохранять их в localStorage, аналитике или диагностике.

## Ответ поставщика

POST /api/bookings/{booking_id}/actions/confirm принимает ConfirmBooking: version самой брони и непустой supplier_booking_number. Сервер очищает крайние пробелы номера. Это внесение сотрудником результата внешнего бронирования: запроса к туроператору из CRM нет.

Подтверждается только pending_confirmation. Сервер повторно проверяет выбранный элемент, состояние заявки и полный состав туристов; сохраняет отдельные неизменяемые Booking.tourists со снимками документов. В одной транзакции бронь получает confirmed, confirmed_at и номер поставщика, заявка — booked, версии обеих записей увеличиваются. У pending/rejected tourist snapshots пусты; исходный список сотрудник читает через /requests/{id}/tourists.

POST /api/bookings/{booking_id}/actions/reject принимает ReasonCommand: version брони и непустую reason. Отклоняется только pending_confirmation. Бронь получает rejected и rejection_reason, её version увеличивается; заявка остаётся offer_prepared, её version также увеличивается. Выбор тура сбрасывается. Менеджер явно выбирает элемент подборки снова (тот же или другой) либо возвращает заявку в работу; следующая попытка создаётся новой записью. Ссылки подборки и формы туристов при отказе остаются действительными, редактирование туристов снова доступно.

Версия создания относится к Request, версии confirm/reject — к Booking. При 409 перечитать обе затронутые карточки; не вычислять следующую версию и не повторять команду с автоматически подставленной новой версией.

## Блокировки связанных действий

Действующими считаются pending_confirmation, confirmed и cancellation_requested. Наличие уже ожидающей брони блокирует публикацию/замену подборки, выбор тура, перевыпуск ссылки подборки, return-to-work, обычные cancel/resume заявки, изменение пожеланий и туристов, выдачу ссылки формы и создание второй брони. Проверки выполняются сервером под общей блокировкой заявки, независимо от показанных кнопок.

Request.active_booking содержит безопасную краткую действующую бронь. tourist_form_editable=false и allowed_actions отражают блокировку; список заявок получает эти проекции пакетно. create_booking предлагается только при выбранном элементе последней подборки, полном совпадающем количестве туристов и отсутствии действующей брони.

Существующая действительная ссылка формы туристов не отзывается при создании/подтверждении брони. Её GET возвращает безопасный шаблон с is_editable=false и closed_reason, без ранее введённых документов; новая отправка получает 409 tourist_form_closed. Повтор ранее успешной отправки с исходными ключом и телом возвращает сохранённый счётчик/версию при активной ссылке. Отзыв/истечение ссылки по-прежнему дают 404. Служебное чтение текущих туристов сохраняется, редактирование закрывается.

## Повторы, аудит и следующий модуль

Все три POST записи требуют Idempotency-Key UUID. Сетевой повтор и повтор после refresh сохраняют исходные тело и ключ. Успешный повтор возвращает ту же бронь в текущем разрешённом представлении: повтор создания после подтверждения вернёт confirmed, не новую попытку. Другой body с тем же ключом — 409 idempotency_conflict. Права перепроверяются после блокировки, в том числе при переназначении; прежний менеджер теряет карточку и повторные команды.

Создание/подтверждение/отказ записывают booking_status в аудит, подтверждение дополнительно записывает request_status. Снимки документов, номер поставщика и свободный текст отказа в историю не копируются. В идемпотентности только хеш команды и ID брони, без копии Booking с паспортами.

Оплата #15 подключена: [правила](payments-integration.md). paid_amount, reserved_payment_amount и remaining_amount рассчитываются по реальным succeeded/pending-платежам; available_payment_amount учитывает резерв и доступен только для confirmed. create_payment предлагается при положительном доступном остатке. Успешные возвраты входят в refunded_amount; paid_amount остаётся валовой оплатой. [Возвраты #35](refunds-integration.md) подключены. API уведомлений и complete реализованы в [#33](payment-notifications-integration.md), отмена реализована в [#34](booking-cancellation-integration.md), возврат реализован в [#35](refunds-integration.md). Pending-попытка не отменяется обычным cancel заявки.

Миграция 0008_bookings добавляет bookings и booking_tourists. Частичный unique по request_id запрещает две действующие брони; составные FK не позволяют связать бронь с элементом другой заявки или снимок с чужим туристом. Сумма проверяется против снимка на уровне БД. Порядок записи: ключ повтора → Client → Request → Booking. Проверки, снимки, версии, аудит и запись повтора фиксируются одной транзакцией; внешнего HTTP-вызова под блокировкой нет.
