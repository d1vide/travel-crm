# Подключение клиентов — серверная часть #12

Реализованы все пять операций clients из [OpenAPI](openapi.json): список, создание, проверка дублей, карточка и изменение. Модели данных: Client, ClientCreate, ClientUpdate, ClientPage, DuplicateCheckResult.

## Формы и чтение

- GET /api/clients: q ищет подстроку имени, email или телефона; page начинается с 1 и ограничена 2147483647, page_size 1–100, по умолчанию 20. sort: -created_at (по умолчанию), full_name, client_number. Неизвестные параметры и пустой q дают 422. total учитывает только доступные карточки; страница за пределами списка возвращает items=[].
- POST /api/clients: отправить только ClientCreate, включая nullable phone/email, preferences/note (допустимы пустые строки) и duplicate_acknowledged. Успех — 201 с Client. UUID, уникальный последовательный client_number, version=1, даты и allowed_actions назначает сервер. Пропуски номеров допустимы.
- GET /api/clients/{client_id}: 200 с Client; отсутствующая или скрытая карточка — одинаковый 404. Отдельные заявки и история общения не вложены в Client: они загружаются своими списками после реализации #13 и #16.
- PUT /api/clients/{client_id}: полная ClientUpdate, включая последнюю прочитанную version. Успех — 200 и новая version. При 409 version_conflict перечитать карточку и предложить повторное применение изменений; не подставлять новую версию автоматически.

Телефон проверяется библиотекой phonenumbers: номер без международного префикса трактуется как RU, международный передаётся с +, добавочные номера не поддерживаются. Исходное оформление телефона сохраняется, для сравнения используется E.164. Email проверяется, очищается от крайних пробелов и приводится к нижнему регистру. Пустой контакт становится null; нужен хотя бы один. Имя очищается от лишних пробелов; поиск не различает регистр и е/ё. Символы % и _ в поиске буквальные. После записи заменить локальную карточку ответом сервера.

## Дубли и права

Перед созданием и при изменении контактов вызвать GET /api/clients/duplicates?phone=...&email=... (отсутствующие контакты не передавать). При редактировании добавить exclude_client_id текущей карточки. Результат:

- matches — краткие доступные карточки, которые можно предложить открыть;
- requires_head_review — обнаружен контакт скрытой карточки; её ID, имя и число совпадений не раскрываются.

При видимых совпадениях показать предупреждение и запросить осознанное подтверждение. После подтверждения отправить duplicate_acknowledged=true. При requires_head_review менеджер обращается к руководителю: один флаг подтверждения не обходит серверную проверку. Руководитель видит все совпадения и может подтвердить создание отдельной карточки. Автоматического слияния нет.

Сохранение повторно проверяет контакты в транзакции: даже после предварительного GET возможен 409 duplicate_contacts либо duplicate_requires_head_review. В этом случае обновить проверку дублей. Подтверждение меняет тело команды, поэтому отправляется с новым ключом. При PUT повторно проверяются только новые нормализованные контакты: изменение примечания или оформления уже существующего номера не требует нового подтверждения.

Менеджер видит клиента по любой своей заявке, включая отменённую. Пока заявок нет — только созданного им клиента. После появления первой заявки доступ определяется ответственными заявок; создатель не сохраняет особых прав. Руководитель видит всех; бухгалтер получает 403, запрос без авторизации — 401. Удаление не реализовано. allowed_actions описывает действия карточки; create_request относится к следующей задаче #13, её серверный маршрут пока отсутствует.

## Повторы

POST и PUT требуют заголовок Idempotency-Key с UUID. Создавать ключ один раз на команду (например, crypto.randomUUID()), сохранять при сетевом повторе и повторе после refresh. Новая команда/изменённое тело получает новый ключ. Порядок JSON-полей не имеет значения.

Успешная команда записывается в PostgreSQL в одной транзакции с карточкой. Повтор возвращает ту же карточку в текущем доступном состоянии, не увеличивает version и не создаёт дубль. Тот же ключ с иным телом даёт 409 idempotency_conflict. Права повторно проверяются: после утраты доступа повтор даст 404. Неуспешная команда не сохраняется. Ключи разделены сотрудником и конкретной HTTP-операцией.

## Граница следующей задачи

Миграция 0002 содержит clients, idempotency_records и базовые поля requests для прав доступа. HTTP API заявок и поля выбора тура добавляются своими задачами; наличие таблицы не означает готовность #13. При создании/переназначении заявки необходимо сначала блокировать строку Client, затем Request: это сериализует изменение доступа с записью карточки. Общий порядок блокировок команд: ключ повтора, нормализованные контакты в сортированном порядке (если используются), Client, Request.

Проверки #12 используют PostgreSQL 16: DTO по зафиксированной схеме, роли/скрытые клиенты, нормализация, дубли, сохранение повторов после переподключения, конфликт версий и конкурентные записи. Проверка полного интерфейса выполняется отдельно после подключения фронтенда.
