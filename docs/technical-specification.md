# Техническое задание

Версия: 0.1 от 26.10.2026. Статус: рабочий проект для обсуждения командой.
Документ составлен по согласованной теме и первоначальному описанию проекта. Подробные требования, сроки и состав отчётных материалов уточняются после получения материалов преподавателя.

## 1. Общие сведения

Название: Travel CRM.
Тема: «Создание программного решения для автоматизации процесса управления клиентскими отношениями в туристической компании».
Учебная дисциплина: ПКИС. Группа: ЭФМО-01-25.
Команда: Наумов Алексей и Холодков.

## 2. Цель и границы

Цель — организовать в одном веб-сервисе работу с клиентом от обращения до бронирования и учёта оплаты.
Учебная версия включает клиентов, заявки, каталог и подбор туров, бронирования, учёт тестовых платежей, историю общения и базовую отчётность.
Внешний каталог туров, бронирование и оплата реализуются тестовыми заглушками. Реальные денежные операции не выполняются.
В текущую версию не входят бухгалтерский учёт, оформление виз, выпуск билетов, мобильное приложение и интеграции с реальными мессенджерами.

## 3. Роли пользователей

| Роль | Доступ |
|---|---|
| Менеджер | Клиенты, заявки, подбор туров, бронирования, тестовые платежи и история общения |
| Руководитель | Возможности менеджера и сводная отчётность |
| Клиент | В рабочем допущении — участник бизнес-процесса без самостоятельного входа; данные вносит менеджер |

Личный кабинет клиента присутствовал в исходном перечне пользователей, но его необходимость и сценарии требуют отдельного согласования. Самостоятельная регистрация и управление пользователями через интерфейс пока не входят в базовую версию. Учётные записи сотрудников создаются при подготовке демонстрационных данных.

## 4. Функциональные требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Вход и выход сотрудников, разграничение прав | Без входа бизнес-данные недоступны; менеджер не получает доступ к сводной отчётности, в том числе через API |
| FR-02 | Создание, просмотр, изменение и поиск клиентов | Карточка хранит ФИО, телефон, email, предпочтения и примечание; обязателен хотя бы один контакт; поиск работает по имени и контактам |
| FR-03 | Ведение заявок клиентов | Заявка связана с клиентом и ответственным менеджером; содержит направление, даты, число туристов, бюджет и комментарий; доступна фильтрация по статусу и ответственному |
| FR-04 | Каталог и подбор туров | Менеджер фильтрует тестовые предложения по направлению, датам, числу туристов и максимальной стоимости и связывает выбранный тур с заявкой |
| FR-05 | Управление бронированием | Для заявки создаётся бронь выбранного тура; результат тестового сервиса сохраняется; при отказе бронь не становится подтверждённой |
| FR-06 | Учёт тестовых платежей | Платёж связан с бронью; хранятся сумма, валюта, дата и статус; повторная обработка одного результата не увеличивает оплаченную сумму |
| FR-07 | История общения | Менеджер добавляет запись о контакте с клиентом с датой, автором, каналом и текстом; записи видны в карточке клиента; фактическая отправка сообщений не выполняется |
| FR-08 | Базовая отчётность | Руководитель выбирает период и видит количество созданных заявок, подтверждённых броней и сумму успешных тестовых платежей; показатели сверяются с исходными данными |
| FR-09 | Обработка ошибок и проверка данных | Отрицательные суммы и бюджет, нулевое число туристов и некорректные даты отклоняются; интерфейс показывает понятную причину ошибки |

Рабочая валюта — RUB; стоимость тура трактуется как общая стоимость на указанное число туристов. В отчёте заявки считаются по дате создания, подтверждённые брони — по дате подтверждения, платежи — по дате успешной обработки. Границы периода включаются; даты отображаются в часовом поясе Europe/Moscow.

## 5. Статусы и правила

- Заявка: новая → в работе → предложение подготовлено → забронирована → завершена. До завершения возможна отмена. Возврат из предложения в работу допускается для повторного подбора.
- Бронь: ожидает подтверждения → подтверждена / отказ; подтверждённую бронь можно отменить через заглушку.
- Платёж: ожидает → успешно / ошибка. Повторная попытка оформляется отдельным платежом с отдельным идентификатором.
- Забронированный статус заявки выставляется после подтверждения брони. Заявка завершается после окончания тура при полной оплате и действующей подтверждённой брони.
- У заявки может быть не более одной действующей брони. После отказа или отмены возможна новая попытка.
- Сумма успешных платежей не может превышать стоимость брони. Оплата допускается только для подтверждённой брони; частичная оплата разрешена.
- Отмена брони с успешными платежами отклоняется с пояснением: возвраты не входят в базовую версию. Бронь без успешных платежей можно отменить, заявка возвращается в работу.
- Изменение цены в каталоге не меняет стоимость существующей брони: в ней сохраняется снимок предложения.
- Карточки и финансовые записи с историей не удаляются физически через интерфейс; ошибочные записи корректируются допустимыми изменениями и статусами.

Таблица переходов статусов и контракт API уточняются до реализации соответствующих сценариев.

## 6. Нефункциональные требования

- Интерфейс и сообщения пользователю — на русском языке; работа в актуальных настольных Chrome и Firefox.
- Сервер проверяет права и входные данные независимо от интерфейса; пароли хранятся в виде стойких хешей; секреты не попадают в репозиторий.
- Для демонстрации используются только вымышленные персональные данные.
- Данные сохраняются в реляционной БД и остаются после перезапуска; схема изменяется миграциями.
- Для локального запуска предоставляются инструкция, пример настроек без секретов и начальные данные.
- Ключевые бизнес-правила покрываются автоматизированными проверками; полный пользовательский сценарий проверяется совместно фронтендом и бэкендом.
- Целевой ориентир для списков: до 2 секунд при 10 000 клиентах и 10 одновременных пользователях в локальном окружении. Это предварительная цель; характеристики окружения и методика проверки фиксируются до нагрузочного тестирования.

## 7. Приёмочный сценарий

1. Запустить систему по инструкции и войти менеджером.
2. Создать вымышленного клиента и заявку с предпочтениями.
3. Подобрать тур из тестового каталога и подтвердить бронь.
4. Выполнить частичную, затем оставшуюся тестовую оплату; проверить итоговую сумму.
5. Добавить запись общения, найти клиента и проверить сохранённую историю после перезапуска.
6. Войти руководителем и сверить отчёт с созданными данными.
7. Проверить отказ бронирования, ошибку оплаты, повтор обработки платежа и ограничения доступа.

## 8. Результаты и открытые вопросы

Результаты: исходный код, документация, миграции, тестовые данные, заглушки, проверки и инструкция для команды приёмки.
До детализации плана уточняются: требования преподавателя, срок сдачи, технологический стек, необходимость кабинета клиента, форма итоговых отчётных документов и условия развёртывания.
