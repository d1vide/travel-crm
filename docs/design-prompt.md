## Текст промта

````text
# Роль
Ты — ведущий продуктовый дизайнер B2B-интерфейсов. Спроектируй дизайн веб-интерфейса учебной CRM-системы для туристической компании: дизайн-систему, ключевые экраны и состояния. Опирайся только на описание ниже; чего в нём нет, не придумывай, а если нужно допущение, пометь его словом «ДОПУЩЕНИЕ».

# Продукт
Travel CRM — единый веб-сервис, в котором менеджер туристической компании «ТрэвелМастер» ведёт клиента от обращения до бронирования, оплаты, отмены и возврата. Сейчас менеджеры работают в разрозненных таблицах и мессенджерах, заявка обрабатывается до 30 минут, бывают дубли заявок и потерянные платежи. Интерфейс должен сокращать ручную работу: минимум кликов, понятные статусы, ошибки с причиной, защита от случайных денежных действий.
Пользователи — сотрудники в офисе, работают весь день, поэтому нужен спокойный, плотный, но читаемый рабочий интерфейс, а не маркетинговый.

# Рамки и допущения
- Язык интерфейса и всех сообщений — русский. Даты в формате ДД.ММ.ГГГГ, часовой пояс Europe/Moscow. Деньги — в рублях (RUB), формат «125 000 ₽» с неразрывным пробелом как разделителем тысяч.
- Основной вид — настольный браузер (Chrome, Firefox), ширина 1280–1920 px. Для трёх страниц клиента по ссылке (см. ниже) дополнительно дай мобильную раскладку 375 px — ДОПУЩЕНИЕ: клиент, вероятно, откроет ссылку с телефона; в ТЗ это не закреплено.
- Реализация на Vue 3 + Naive UI (naive-ui 2.x). Проектируй так, чтобы экраны собирались из стандартных компонентов Naive UI (n-layout, n-menu, n-data-table, n-form, n-input, n-select, n-date-picker, n-tag, n-steps, n-card, n-modal, n-drawer, n-alert, n-empty, n-skeleton, n-message, n-badge, n-tabs, n-descriptions, n-timeline). Свою визуальную идентичность выражай через тему Naive UI (themeOverrides: цвета, радиусы, шрифт, плотность), а не через кастомные компоненты. Для каждого нестандартного компонента укажи, из чего он собирается.
- Платёжный сервис — тестовая заглушка, деньги не двигаются. На странице оплаты клиента карточные данные НЕ вводятся: клиент выбирает один из управляемых тестовых исходов (успех, отказ, тайм-аут). Заметно и честно отметь на этой странице, что это тестовый режим.
- Все данные в макетах — вымышленные (ФИО, телефоны, паспорта, номера броней). Паспортные данные в макетах не должны выглядеть как реальные.

# Роли и доступ
| Роль | Что видит и делает |
|---|---|
| Менеджер | Только закреплённые за ним заявки и их клиентов: создание клиентов и заявок, подбор туров и подборки, данные туристов, брони, платежи, отмена и возврат по своим заявкам, записи общения |
| Руководитель (РОП) | Всё то же по всем заявкам; смена ответственного менеджера; просмотр оплат и переписки; сводный отчёт; «Рабочее место руководителя» |
| Бухгалтер | Только «Оплаты и возвраты»: просмотр и проверка сумм. Не видит заявки, клиентов, паспорта |
| Клиент | Не входит в систему. По непредсказуемой ссылке от менеджера открывает три страницы: подборка туров, форма данных туристов, оплата |

Интерфейс скрывает недоступные разделы и действия, но при прямом заходе показывает страницу «Нет доступа» (403), а не пустой экран.

# Информационная архитектура сотрудника
Боковое меню (ширина 240 px) + верхняя панель (имя пользователя, тег роли, уведомления, «Выйти»). Разделы и роли:
1. Заявки — менеджер, РОП (стартовая страница)
2. Клиенты — менеджер, РОП
3. Каталог туров — менеджер, РОП
4. Оплаты и возвраты — РОП, бухгалтер (стартовая для бухгалтера)
5. Рабочее место руководителя — только РОП
6. Отчёт — только РОП
Плюс: экран входа, 403, 404, колокольчик уведомлений в верхней панели.

# Экраны, которые нужно спроектировать

## Сотрудник
1. **Вход.** Логин и пароль, ошибка неверных данных, состояние загрузки. Без регистрации и восстановления пароля (их нет в объёме).
2. **Список заявок.** Таблица: номер, клиент, направление, даты поездки, число туристов, бюджет, статус заявки, ответственный, дата создания. Фильтры по статусу и ответственному (у менеджера фильтр ответственного не нужен). Поиск. Кнопка «Новая заявка». Пустое состояние для нового менеджера.
3. **Создание заявки и клиента.** Сначала поиск клиента по имени, телефону, email. Если найдено совпадение по контактам — блок «Возможный дубль» с карточками найденных клиентов и выбором: «Это тот же клиент» / «Нет, создать нового». Автоматического слияния нет, решение всегда за менеджером. Форма клиента: ФИО, телефон, email, предпочтения, примечание; обязателен хотя бы один контакт. Форма заявки: направление, даты, число туристов, бюджет, пожелания. Валидация: отрицательный бюджет, ноль туристов, дата окончания раньше начала — отклоняются с понятной причиной у поля.
4. **Карточка заявки — главный экран продукта.** Должен за один взгляд показывать, на каком шаге заявка и что делать дальше.
   - Шапка: номер, клиент (ссылка), ответственный, четыре отдельных статуса (заявка, бронь, платёж, возврат) — см. раздел «Статусы».
   - Полоса прогресса по жизненному циклу заявки (n-steps).
   - Блок «Следующее действие» с одной главной кнопкой по текущему состоянию.
   - Вкладки или секции: «Пожелания», «Подборка», «Туристы», «Бронь», «Платежи и возвраты», «История общения», «История изменений».
   - Копирование ссылки для клиента (подборка, форма туристов, оплата) одной кнопкой с подтверждением «Ссылка скопирована»; рядом — напоминание, что менеджер отправляет её клиенту сам, вне системы.
5. **Каталог туров и подбор.** Список предложений с фильтрами: направление, даты, число туристов, максимальная стоимость. Карточка предложения: название, направление, даты, состав, цена (общая на указанное число туристов). Выбор нескольких туров в «корзину подборки» (минимум один), кнопка «Создать подборку» заблокирована при пустой корзине с пояснением почему. После создания — ссылка на страницу клиента и предпросмотр.
6. **Подборка в заявке.** Список туров подборки, отметка «Выбор клиента» (менеджер записывает выбор клиента вручную), кнопка «Создать бронь по выбранному туру».
7. **Данные туристов.** Список туристов заявки, статус «форма не заполнена / заполнена клиентом». Паспортные данные по умолчанию скрыты (маска), показываются по явному действию только тем ролям, которым они нужны, с пометкой об этом. Ручное редактирование.
8. **Бронь.** Снимок тура и цены на момент создания (подпись «Цена зафиксирована, изменения каталога на неё не влияют»). Форма «Ответ поставщика»: подтверждено / отказ, номер брони поставщика, комментарий. Кнопка «Подтвердить» неактивна, пока не выполнены условия: выбран тур, есть данные туристов, указана стоимость, есть подтверждение поставщика — показать чек-лист условий с отметками. При отказе — статус «Отказ», объяснение, кнопка «Новая попытка бронирования» (у заявки не более одной действующей брони).
9. **Платежи по брони.** Создание платежа доступно только для подтверждённой брони: сумма (не больше остатка к оплате), кнопка «Создать платёж и получить ссылку». Таблица платежей: сумма, валюта, внешний номер операции, дата, статус. Показатели: стоимость брони / оплачено / остаток. Частичная оплата допустима. Платёж в ожидании (тайм-аут) остаётся «Ожидает» с видимой причиной; повторная попытка — это новый платёж с новым номером, а не «повторить» старый. Один внешний номер учитывается один раз — в интерфейсе повтор не должен выглядеть как двойное зачисление.
10. **Отмена и возврат.** Сценарий отмены: (а) записать просьбу клиента об отмене → статус брони «Отмена запрошена»; (б) внести подтверждение поставщика → «Отменена». Если успешных платежей не было — заявка возвращается в работу, об этом сообщение. Если платежи были — отмена НЕ возвращает деньги: отдельный блок «Возврат» с суммой (положительная, не больше полученной оплаты минус прошлые возвраты, показать лимит), статус «В обработке → Выполнен / Ошибка». Сообщать «Возврат выполнен» можно только после ответа платёжного сервиса. Модальное подтверждение денежных действий с итоговой суммой.
11. **История общения.** Лента записей: дата, автор, канал (телефон, лично, мессенджер, другое), текст. Форма «Добавить запись». Только фиксация контакта менеджером; отправки сообщений нет, и в интерфейсе не должно быть кнопок «Отправить» в мессенджер/почту.
12. **Список и карточка клиента.** Поиск по имени и контактам, карточка с контактами, предпочтениями, примечанием, списком заявок и историей общения.
13. **Оплаты и возвраты (РОП, бухгалтер).** Таблица всех платежей и возвратов: заявка, клиент, сумма, статус, внешний номер, дата. Фильтры по статусу и периоду. Бухгалтер только просматривает и проверяет суммы, без действий над заявкой.
14. **Рабочее место руководителя.** Все заявки со всеми статусами; быстрая смена ответственного менеджера (выбор + подтверждение, запись попадает в историю); просмотр переписки менеджеров; лента поступлений оплат. Кнопка «Открыть заявку».
15. **Отчёт.** Выбор периода (границы включаются) и четыре числа: созданные заявки, подтверждённые брони, сумма успешных тестовых платежей, сумма возвратов. Простая таблица или крупные числа. Графиков, настраиваемых отчётов и выбора визуализации НЕТ в объёме — не рисовать.
16. **Уведомления.** Колокольчик со счётчиком непрочитанных и выпадающий список: «Оплата 50 000 ₽ по заявке №… учтена». Менеджер видит оплаты по своим заявкам, РОП — все поступления. Одно уведомление на один платёж.
17. **Служебные.** 403 «Нет доступа», 404, глобальная ошибка сети/сервера.

## Клиент (без входа, по ссылке) — минималистичный брендированный вид без меню CRM
1. **Страница подборки.** Заголовок «Подборка туров для вас», карточки только туров этой подборки: название, направление, даты, состав, цена. Выбор тура кнопкой в объём НЕ входит — клиент сообщает выбор менеджеру вне системы, поэтому кнопка «Забронировать» не рисуется; вместо неё подсказка «Сообщите менеджеру, какой тур вам подходит» и контакт менеджера. ДОПУЩЕНИЕ: показать имя менеджера.
2. **Форма данных туристов.** Для каждого туриста блок полей (ФИО, дата рождения, паспортные данные и т. п. — состав уточнить, пометить как ДОПУЩЕНИЕ), кнопки «Добавить туриста»/«Удалить», проверка обязательных полей с причиной у поля, экран успешной отправки. Короткое пояснение, кому видны паспортные данные. Защита от повторной отправки (кнопка блокируется после нажатия).
3. **Страница оплаты (заглушка).** Название тура, сумма к оплате, остаток, пометка «Тестовый режим — деньги не списываются». Три управляемых исхода: «Успешная оплата», «Отказ», «Тайм-аут» с результирующими экранами: успех (сумма учтена), отказ (понятная причина, как действовать), ожидание (платёж не подтверждён, обратитесь к менеджеру). Поля банковской карты НЕ рисовать.
4. **Недействительная ссылка.** Нейтральный экран без раскрытия, существует ли заявка.

# Статусы (обязательная часть дизайн-системы)
Четыре независимых статуса, каждый со своим тегом и семантикой цвета. Подтверждение брони не означает оплаты, отмена брони не означает возврата — это должно быть видно в интерфейсе: четыре статуса отображаются раздельно, а не одним «общим» статусом.
- Заявка: Новая → В работе → Предложение подготовлено → Забронирована → Завершена; также Отменена. Возврат из «Предложение подготовлено» в «В работе» допустим.
- Бронь: Ожидает подтверждения → Подтверждена / Отказ; Подтверждена → Отмена запрошена → Отменена.
- Платёж: Ожидает → Успешно / Ошибка.
- Возврат: В обработке → Выполнен / Ошибка.
Для каждого статуса задай цвет (светлая и тёмная тема), иконку и подпись; цвет никогда не единственный носитель смысла (контраст не ниже WCAG AA, дублируй текстом или иконкой). Не используй красный для «Ожидает» и «В обработке».

# Сквозные паттерны и состояния
Для каждого экрана и каждого компонента данных покажи состояния: загрузка (skeleton), пусто (n-empty с понятным следующим шагом), ошибка загрузки с кнопкой «Повторить», ошибка валидации у поля, ошибка сервера (формат: код + сообщение + поля), отсутствие прав.
- Сбой внешнего сервиса: сущность остаётся «в ожидании», сотрудник видит причину ошибки в тексте, а не просто «Ошибка».
- Деструктивных действий нет: карточки и финансовые записи с историей не удаляются физически, кнопки «Удалить» для заявок, клиентов, броней, платежей, возвратов НЕ рисовать; исправление — через допустимые изменения и статусы. Удалять можно только черновые элементы в формах (турист в форме, тур из корзины подборки).
- Денежные действия (создать платёж, оформить возврат, подтвердить отмену, сменить ответственного) — всегда через подтверждение с итогом («Вернуть 25 000 ₽ по платежу №…»), кнопки блокируются на время запроса.
- Неактивные кнопки всегда объясняют причину (подсказка рядом, не только tooltip).
- История изменений: смена ответственного и денежных статусов записывается; покажи ленту (n-timeline): кто, когда, что изменилось.
- Маскирование паспортных данных и невозможность увидеть чужие заявки (для менеджера) — часть дизайна, а не оговорка.

# Что в объёме НЕ входит — НЕ проектируй
Telegram/email/телефония и «единое окно переписки», договор (шаблон, скан, подписание), рекомендации, избранное, лайки туров, бронирование туров кнопкой клиента, отзывы и NPS, уведомление «заявка без ответа 10 минут», настраиваемые отчёты и графики, интеграция с туроператором, 1С, банком, личный кабинет клиента, самостоятельная регистрация и управление пользователями, мобильное приложение для сотрудников.

# Визуальный стиль
Деловой, спокойный, доверительный; ориентир — современные рабочие инструменты (Linear, Notion, Stripe Dashboard) без перегруженности. Плотные таблицы, крупные читаемые статусы, один акцентный цвет (предложи по смыслу «путешествия», например сдержанный тёмно-синий или бирюзовый) и нейтральная серая шкала. Светлая тема основная, тёмная — вариант. Шрифт — системный без засечек или Inter с полной кириллицей. Базовый размер текста 14 px, отступы по сетке 4/8 px, радиус 6–8 px. Иконки — один набор (например, Ionicons, как в экосистеме Naive UI).
Логотип и название «Travel CRM» в левом верхнем углу меню; для страниц клиента — название «ТрэвелМастер».

# Что нужно получить на выходе
1. **Дизайн-токены**: палитра (светлая/тёмная), семантические цвета статусов, типографика, сетка и отступы, радиусы, тени — в виде, переносимом в `themeOverrides` Naive UI (JSON или таблица значений).
2. **Библиотека компонентов** с вариантами и состояниями: теги статусов, шапка заявки с четырьмя статусами, полоса прогресса, таблицы со строками и фильтрами, формы с ошибками, карточка тура, блок «Следующее действие», лента истории, модальное подтверждение денежных действий, уведомление, пустые и ошибочные состояния.
3. **Макеты всех экранов** из списка выше для ролей менеджер, РОП, бухгалтер и для трёх страниц клиента (десктоп; клиентские страницы — ещё и 375 px). Для каждого экрана — основное состояние и минимум два состояния ошибки/пусто/загрузки.
4. **Сквозные сценарии (flows)**, нарисованные последовательностью экранов:
   А. Менеджер: вход → новая заявка с проверкой дубля клиента → подбор туров → подборка и ссылка клиенту → клиент открывает ссылку (страница подборки) → запись выбора → форма туристов по ссылке → создание брони → ответ поставщика «подтверждено» → платёж и ссылка оплаты → клиент платит частично, затем остаток → уведомление менеджеру → запись общения.
   Б. Отмена оплаченной брони → отдельный возврат с проверкой лимита суммы → статусы отмены и возврата видны раздельно.
   В. Отказ поставщика; ошибка оплаты; тайм-аут (платёж «Ожидает» с причиной); повтор того же результата платёжным сервисом (сумма не удваивается).
   Г. РОП: список всех заявок → смена ответственного → просмотр переписки → оплаты → отчёт за период. Бухгалтер: оплаты и возвраты.
   Д. Попытка доступа к недоступному разделу (403) и недействительная ссылка клиента.
5. **Сопоставление с Naive UI**: для каждого экрана — из каких компонентов собирается и какие нестандартные места требуют доработки.
6. **Краткое обоснование** ключевых дизайн-решений: как интерфейс предотвращает ошибки (дубли клиентов, лишние платежи, возврат больше оплаты, ложный «успешный возврат»).
7. **Список допущений и открытых вопросов** (всё, что помечено «ДОПУЩЕНИЕ»).

# Критерии качества
- Весь приёмочный сценарий (вход менеджером → клиент и заявка → подборка по ссылке → данные туристов → бронь → частичная и полная оплата → общение → отмена и возврат → вход РОП и бухгалтером) проходится по макетам без «белых пятен».
- В любой момент на карточке заявки понятно: текущий статус каждой из четырёх сущностей, что мешает следующему шагу и какое действие главное.
- Ни один макет не нарушает правил доступа и списка «НЕ входит в объём».
- Контраст и размеры соответствуют WCAG 2.1 AA, интерфейс управляется с клавиатуры (видимый фокус), все поля с подписями.
- Формулировки на русском, без англицизмов и без технического жаргона; сообщения об ошибках объясняют причину и что делать.
````
