# Архитектура репозитория и запуск через Docker

Дата: 12.11.2026. Статус: проект на согласовании. Не заменяет `docs/architecture.md`, а уточняет его: выбирает технологии и способ запуска, которые там оставлены открытыми.

## 1. Принятые решения

| Область | Решение |
|---|---|
| Бэкенд | Python 3.12, FastAPI, SQLAlchemy, Alembic; менеджер зависимостей `uv`; `ruff`, `pytest` |
| Фронтенд | Vue 3, TypeScript, Vite, Pinia; Node 22 LTS; `eslint`, `prettier`, `vitest`, `vue-tsc` |
| БД | PostgreSQL 16, схема только через миграции |
| Заглушки | Отдельный сервис `stubs/` (FastAPI) в своём контейнере, бэкенд обращается к нему по HTTP через адаптеры |
| Репозиторий | Монорепо |
| Точка входа | nginx раздаёт собранный фронтенд и проксирует `/api` на бэкенд; один origin, без CORS |
| Авторизация | JWT: access в памяти фронтенда, refresh в httpOnly-cookie |
| Контракт API | Код бэкенда (Pydantic) является источником; OpenAPI коммитится в `docs/api/openapi.json` |
| Ревью | Не требуется; страховка качества — CI |

## 2. Структура репозитория

```
travel-crm/
├─ frontend/             Vue 3 + TS + Vite
├─ backend/
│  ├─ app/
│  │  ├─ core/           конфиг, БД, JWT и безопасность
│  │  ├─ modules/        auth, clients, requests, tours, bookings,
│  │  │                  payments, communications, reports
│  │  └─ adapters/       клиенты заглушек (tours, payments)
│  ├─ alembic/           миграции
│  └─ tests/
├─ stubs/                сервис заглушек туроператора и платежей
├─ deploy/nginx.conf     раздача фронтенда и прокси /api
├─ docs/                 документация; docs/api/openapi.json
├─ docker-compose.yml
├─ .env.example
└─ .github/
```

Модуль бэкенда содержит роуты, схемы, сервис и модели. К данным другого модуля обращаются через его сервис, а не через его таблицы.

## 3. Docker Compose

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL с томом; порт открыт только на `127.0.0.1:5432` |
| `backend` | При старте выполняет `alembic upgrade head`; демо-данные создаются командой или флагом `SEED_DEMO=true` |
| `stubs` | Сценарии успеха, отказа и тайм-аута для каталога, бронирования и платежей |
| `web` | Многостадийная сборка: Vue собирается и ложится в nginx; единственный внешний порт (8080) |

Конфигурация задаётся переменными окружения. В репозитории хранится только `.env.example` без секретов.

### Режимы работы

- Ежедневная разработка: `docker compose up -d db stubs`, фронтенд через `npm run dev` (Vite проксирует `/api` на `localhost:8000`), бэкенд через `uvicorn --reload`.
- Проверка сборки и демонстрация: `docker compose up --build`, приложение на `http://localhost:8080`.

## 4. Контракт API и типы

1. На этапе проектирования (Issue «Согласовать контракт API») бэкенд описывает Pydantic-схемы и роуты-пустышки (ответ 501) по FR-01…FR-09 и экспортирует `docs/api/openapi.json`.
2. Фронтенд генерирует типы и клиент из этого файла (`openapi-typescript`, `openapi-fetch`) в `frontend/src/api/`.
3. До готовности бэкенда фронтенд работает с моком по тому же файлу (Prism). Переключение на реальный бэкенд — переменная `VITE_API_TARGET` в проксировании Vite.
4. Кто меняет контракт, обновляет `openapi.json` в том же PR и сообщает об этом в связанном Issue. Несовместимые изменения (удаление или переименование поля) помечаются `BREAKING` в заголовке PR.
5. Единый формат ошибок `{code, message, fields[]}`. Ошибки валидации FastAPI (422) приводятся к нему же, чтобы формы показывали причину по полю (FR-09).
6. Префикс API — `/api`, без версии.

## 5. Авторизация (JWT)

- `POST /api/auth/login` возвращает `access_token` и профиль с ролью; refresh устанавливается cookie `HttpOnly; SameSite=Strict; Path=/api/auth`.
- `POST /api/auth/refresh` выдаёт новый access и ротирует refresh. Хеш refresh хранится в таблице `refresh_tokens`.
- `POST /api/auth/logout` отзывает refresh и очищает cookie.
- `GET /api/auth/me` возвращает текущего пользователя.
- Время жизни: access около 15 минут, refresh около 7 дней.
- Фронтенд хранит access в Pinia. При старте приложения сначала вызывается refresh. HTTP-клиент при ответе 401 один раз обновляет токен и повторяет запрос; параллельные запросы ждут один общий refresh.
- Права проверяются на сервере на каждом защищённом эндпоинте (зависимость FastAPI по роли). Guard роутов на фронтенде нужен только для удобства. Менеджер не получает отчёт через API (FR-01).

## 6. Проверки и CI

Тесты бэкенда: `pytest` с тестовой БД PostgreSQL из compose. В первую очередь покрываются бизнес-правила ТЗ: переходы статусов, одна действующая бронь на заявку, сумма платежей не больше стоимости брони, идемпотентность платежа, отказ в отмене оплаченной брони, права по ролям на эндпоинтах.

Тесты фронтенда: `vitest` для логики (обновление токена, валидация форм), `vue-tsc`, `eslint`. Сквозной приёмочный сценарий автоматизируется Playwright на полном стеке в Docker на этапе 8.

GitHub Actions на каждый PR и push в `main`:

- `backend`: `ruff`, `pytest` с сервисом Postgres;
- `frontend`: `eslint`, `vue-tsc`, `vitest`, `vite build`;
- `contract`: `docs/api/openapi.json` соответствует коду;
- `docker`: `docker compose build` проходит.

Проверки нужно сделать обязательными в ruleset `main-review`; изменять ruleset может только владелец репозитория (@d1vide).

Task runner (`make`) не вводится: команды описываются в README. При необходимости позже добавляется `justfile`.
