# Архитектура системы

Версия 0.1 от 26.10.2026. Предварительное описание на основе исходной схемы команды. Технологии пока не выбраны.

## Общая схема

Веб-интерфейс обращается к единому бэкенду через API. Бэкенд проверяет права, выполняет бизнес-правила и работает с реляционной БД. Внешние сервисы скрыты за адаптерами; в учебной версии используются заглушки.

~~~mermaid
flowchart LR
    Staff[Менеджер и руководитель] --> UI[Веб-интерфейс]
    UI <-->|HTTP API| Backend[Бэкенд]
    Backend <-->|SQL| DB[(Реляционная БД)]
    Backend <-->|Адаптер каталога и бронирования| Tours[Заглушка туроператора]
    Backend <-->|Адаптер платежей| Payments[Заглушка оплаты]
~~~

Клиент обращается в туристическую компанию, а менеджер вносит данные в CRM. Самостоятельный доступ клиента требует отдельного решения и пока не включён в схему учебной версии.

## Компоненты

| Компонент | Ответственность |
|---|---|
| Фронтенд | Формы и списки, поиск, фильтры, отображение статусов и ошибок, экраны отчётности |
| Бэкенд | Аутентификация и права, клиенты и заявки, подбор, жизненный цикл броней и платежей, история общения, отчёты |
| База данных | Пользователи, клиенты, предпочтения, заявки, снимки туров, брони, платежи, записи общения |
| Адаптер каталога и бронирования | Получение предложений, подтверждение и отмена брони, преобразование ответов заглушки |
| Адаптер платежей | Создание тестового платежа и обработка его результата с защитой от повторов |

Предлагается модульный монолит: один сервер приложения с разделением кода по предметным областям. Отдельные микросервисы для базовой учебной версии не требуются. Заглушки могут быть внутренними адаптерами или локальными HTTP-сервисами; способ выбирается на этапе проектирования.

## Основные сущности

- User: учётная запись сотрудника и роль.
- Client: контакты, предпочтения, примечание.
- Request: клиент, ответственный менеджер, пожелания, бюджет, даты и статус.
- TourOffer: предложение из тестового каталога.
- Booking: заявка, идентификатор внешней брони, снимок тура и цены, статус, дата подтверждения.
- Payment: бронь, сумма, валюта, внешний идентификатор операции, статус и дата успешной обработки.
- Communication: клиент, при необходимости заявка, автор, дата, канал и текст записи.

Клиент имеет много заявок и записей общения; заявка — историю попыток бронирования; бронь — несколько платежей. У заявки не более одной действующей брони. Точная ER-диаграмма, ограничения и индексы готовятся до реализации БД.

## Границы и согласованность

- Фронтенд не подключается к БД; окончательное решение о правах и допустимости операции принимает сервер.
- Изменения статусов и финансовых сумм выполняются транзакционно с учётом параллельных запросов.
- Повторный результат платежа определяется по уникальному идентификатору операции и не создаёт повторное зачисление.
- При тайм-ауте бронирования система не считает бронь подтверждённой без подтверждения результата; повтор запроса не должен создавать вторую действующую бронь.
- Секреты задаются настройками окружения; в репозитории будет только пример конфигурации без секретов.
- Реальные карточные данные не принимаются и не хранятся. Заглушки используют тестовые идентификаторы и управляемые сценарии успеха, отказа и тайм-аута.

## Что уточнить на этапе проектирования

Технологический стек, схема аутентификации, контракт API и ошибок, модель данных, переходы статусов, протоколы заглушек и способ запуска. Эти решения фиксируются в документации до реализации зависящих от них задач.
