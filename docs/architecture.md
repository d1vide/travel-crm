## Технологический стек

| Область | Решение |
|---|---|
| Фронтенд | Vue 3, TypeScript, Vite, Pinia |
| Бэкенд | Python 3.12, FastAPI, SQLAlchemy, Alembic |
| База данных | PostgreSQL 16, схема только через миграции |
| Заглушка платёжного сервиса | Отдельный сервис на FastAPI в своём контейнере: ссылка на оплату, страница оплаты, результат и возврат |
| Точка входа | nginx: раздаёт собранный фронтенд и проксирует `/api` на бэкенд |
| Запуск | Docker Compose; репозиторий — монорепо |
| Авторизация | JWT: access в памяти фронтенда, refresh в httpOnly-cookie |

## Общая схема

Веб-интерфейс обращается к единому бэкенду через API. Бэкенд проверяет права, выполняет бизнес-правила и работает с реляционной БД. Внешние сервисы скрыты за адаптерами; в учебной версии используются заглушки. Браузер видит один адрес: nginx отдаёт интерфейс и проксирует запросы `/api`, поэтому настройка CORS не нужна.

~~~mermaid
flowchart LR
    Staff[Менеджер и руководитель] --> Web[nginx: фронтенд Vue и прокси /api]
    Web <-->|HTTP /api| Backend[Бэкенд FastAPI]
    Backend <-->|SQL| DB[(PostgreSQL)]
    Backend <-->|Адаптер платежей, HTTP| Stubs[Заглушка платёжного сервиса]
~~~

Клиент обращается в туристическую компанию, а менеджер вносит данные в CRM. Клиент не входит в систему: по ссылке от менеджера он открывает страницу подборки, форму данных туристов и страницу оплаты. Бронирование у туроператора менеджер выполняет вне системы и вносит ответ поставщика в CRM, поэтому заглушка туроператора в первой версии не нужна. Telegram, договор и другие каналы в первую версию не входят.

## Компоненты

| Компонент | Ответственность |
|---|---|
| Фронтенд | Формы и списки, поиск, фильтры, отображение статусов и ошибок, рабочее место руководителя, экраны отчётности, страницы клиента по ссылке |
| Бэкенд | Аутентификация и права, клиенты и заявки, каталог и подборки, жизненный цикл броней, отмена, платежи и возвраты, история общения, уведомления, отчёты |
| База данных | Пользователи, клиенты, предпочтения, заявки, туристы, каталог, подборки, снимки туров, брони, платежи, возвраты, записи общения, история изменений, уведомления |
| Страницы клиента | Подборка, форма данных туристов и страница оплаты по ссылке без входа; ссылка содержит непредсказуемый токен |
| Адаптер платежей | Создание тестового платежа и ссылки на оплату, получение результата и возврата, защита от повторов |

Бэкенд — модульный монолит: один сервер приложения с разделением кода по предметным областям (`auth`, `clients`, `requests`, `tours` — каталог и подборки, `bookings` — брони, туристы и отмена, `payments` — платежи и возвраты, `communications` — записи общения, `notifications`, `reports`). К данным другого модуля обращаются через его сервис, а не через его таблицы. Отдельные микросервисы, кроме сервиса заглушки, не вводятся. Заглушка платёжного сервиса работает отдельным HTTP-сервисом, бэкенд обращается к ней через адаптер; это позволяет проверять реальные тайм-ауты и повторы.

## Авторизация

- `POST /api/auth/login` возвращает access-токен и профиль с ролью; refresh-токен устанавливается cookie `HttpOnly; SameSite=Strict; Path=/api/auth`.
- `POST /api/auth/refresh` выдаёт новый access и заменяет refresh; хеш refresh хранится в БД, поэтому `POST /api/auth/logout` реально отзывает токен.
- Время жизни: access около 15 минут, refresh около 7 дней.
- Фронтенд хранит access только в памяти. При старте сначала запрашивается refresh; при ответе 401 клиент один раз обновляет токен и повторяет запрос.
- Права проверяются на сервере на каждом защищённом эндпоинте; ограничение доступа на фронтенде служит только удобству. Менеджер не получает отчёт и чужие заявки через API.
- Роли: менеджер, руководитель, бухгалтер. Страницы клиента (подборка, форма туристов, оплата) не используют JWT: доступ определяется непредсказуемым токеном в ссылке, который открывает только свои данные и не даёт доступа к остальным функциям.

## Контракт API

Источником контракта служит код бэкенда (схемы Pydantic). Файл `docs/api/openapi.json` экспортируется из него и хранится в репозитории; по нему фронтенд генерирует типы и клиент, а до готовности бэкенда работает с моком. Префикс API — `/api`. Ошибки возвращаются в едином формате `{code, message, fields[]}`, включая ошибки валидации, чтобы интерфейс показывал причину по полю (FR-09).

## Запуск

- Ежедневная разработка: `docker compose up -d db stubs`, фронтенд через `npm run dev`, бэкенд через `uvicorn --reload`. Vite проксирует `/api` на локальный бэкенд.
- Проверка сборки и демонстрация: `docker compose up --build`, приложение на `http://localhost:8080`.
- Конфигурация задаётся переменными окружения; в репозитории хранится только `.env.example`.

## Основные сущности

- User: учётная запись сотрудника и роль.
- Client: контакты, предпочтения, примечание.
- Request: клиент, ответственный менеджер, пожелания, бюджет, даты и статус.
- TourOffer: предложение из тестового каталога.
- Selection: подборка для заявки, список туров, токен ссылки, выбор клиента.
- Tourist: данные туриста заявки; передаются клиентом через форму по ссылке.
- Booking: заявка, туристы, номер брони поставщика, снимок тура и цены, статус брони и статус отмены, дата подтверждения.
- Payment: бронь, сумма, валюта, внешний идентификатор операции, статус и дата успешной обработки.
- Refund: платёж, сумма, статус и дата успешной обработки.
- Communication: клиент, при необходимости заявка, автор, дата, канал и текст записи.
- Notification: получатель, событие и признак прочтения.
- AuditRecord: запись истории о смене ответственного или денежного статуса.

Клиент имеет много заявок и записей общения; заявка — подборки и историю попыток бронирования; бронь — несколько платежей; платёж — несколько возвратов. У заявки не более одной действующей брони. Точная ER-диаграмма, ограничения и индексы готовятся до реализации БД.

## Границы и согласованность

- Фронтенд не подключается к БД; окончательное решение о правах и допустимости операции принимает сервер.
- Изменения статусов и финансовых сумм выполняются транзакционно с учётом параллельных запросов.
- Повторный результат платежа определяется по уникальному идентификатору операции и не создаёт повторное зачисление.
- Бронь считается подтверждённой и отменённой только после того, как менеджер внёс ответ поставщика; повторная отправка не создаёт вторую действующую бронь.
- Статусы брони, платежа, отмены и возврата хранятся отдельно: подтверждение не означает оплаты, а отмена — возврата денег.
- Изменения ответственного менеджера и денежных статусов записываются в историю.
- Секреты задаются настройками окружения; в репозитории хранится только пример конфигурации `.env.example` без секретов.
- Реальные карточные данные не принимаются и не хранятся. Заглушки используют тестовые идентификаторы и управляемые сценарии успеха, отказа и тайм-аута.
